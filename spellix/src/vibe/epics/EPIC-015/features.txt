Goal

* Add a new page called the `Decision` page.
* A decision is a question with 3 possible answers.
* Each answer has a percentage chance of producing a good, neutral, or bad outcome.
* In this feature, implement:

  * the Decision page route.
  * the Decision page layout.
  * the decision question data.
  * random question selection.
  * 3 full-width answer buttons.
  * weighted good / neutral / bad outcome resolution.
  * temporary outcome display.
  * Continue flow back to the board.
  * debug menu access.
* Actual rewards and punishments are out of scope for this feature.

Concept Summary

* A decision contains:

  * one question.
  * three fixed choices.
  * each choice has a good, neutral, and bad chance.
  * each outcome has:

    * an outcome result, such as `Gain a Small Heal potion`, `Nothing`, `Lose a token`, or `Lose your next turn`.
    * outcome text, usually a longer narrative sentence explaining what happened.
* The player must choose one of the 3 options.
* The game then rolls against that choice’s good / neutral / bad chances.
* For now, the game only displays the selected outcome.
* Later features will implement the actual outcome effects.

Terminology Note

* The source table uses `Choice Natural Chance`.
* In implementation, treat this as `Choice Neutral Chance`.
* Use `neutral` everywhere in code unless the existing project already uses another spelling.

Outcome Resolution Requirement

* When a player clicks a choice button, use that choice’s chances to randomly decide the outcome.
* Possible outcomes:

  * good.
  * neutral.
  * bad.
* Actual outcome effects are out of scope.
* For now, display:

  * the outcome text.
  * the outcome result.
* Example:

  * outcome text: `The voice belongs to a grateful spirit, which rewards your kindness.`
  * outcome result: `Gain a Small Heal potion`

Suggested Resolution Logic

```js id="z4e6qp"
function resolveDecisionOutcome(chances) {
  const roll = Math.random() * 100;

  if (roll < chances.good) {
    return "good";
  }

  if (roll < chances.good + chances.neutral) {
    return "neutral";
  }

  return "bad";
}
```

Chance Validation Requirement

* Each choice’s good, neutral, and bad chance should total `100`.
* If a choice does not total `100`, log a clear development warning.
* If an outcome has a `0` chance, it should never be selected.
* Some neutral outcomes in the table are `N/A` because their chance is `0`.
* Do not display `N/A` outcomes unless bad data causes them to be selected.

Outcome Effect Placeholder Requirement

* This feature should not apply the actual effect from the outcome result.
* Do not actually:

  * grant potions.
  * grant tokens.
  * remove tokens.
  * remove potions.
  * reduce health.
  * skip turns.
* Only display the result and narrative text.
* Later features will implement each outcome type.

Manual Background Selection Requirement

* Add or reuse a temporary debug/manual background selector for the Decision page.
* This should work like the current battle background testing approach.
* The background selector should be development/debug support only.
* The Decision page should ultimately be able to use the square landed on, but automatic square connection is not required in this feature.

No `ul` / `li` Requirement

* Do not use `ul` or `li` anywhere in the new Decision page UI.
* Use `div` elements with flex or grid layouts.

Out Of Scope

* Do not implement actual good rewards.
* Do not implement actual neutral effects.
* Do not implement actual bad punishments.
* Do not connect decisions to real board square encounter generation yet.
* Do not implement Good Decisions potion behaviour yet.
* Do not implement decision-specific animations yet.
* Do not add cancel, back, skip, close, retreat, or escape buttons.
* Do not redesign battle, cave, river, loot, or board pages.
* Do not add unrelated encounter systems.

Assumptions

* The current player image can be reused from existing battle, mini-game, or player display components.
* The modal background and button styles can be reused from existing modal components.
* Until automatic square-background selection exists, manual background selection is acceptable as it is for battles.
* Outcome result labels are temporary display labels in this feature, but should be structured clearly enough for later implementation.

  * the Decision page exists.
  * it can be opened from the debug menu under Mini Games.
