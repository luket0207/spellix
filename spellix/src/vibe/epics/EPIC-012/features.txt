Feature-001: Add potion trigger UI and confirmation flow for Board and Battle potions

Status

* done

Completion Notes

* Added Board-context Use controls for `Board` and `Both` potions while keeping all owned `Battle` and `Mini` potions visible without active controls and reserving equal button space on every board card.
* Added a centred Battle potion section above the existing dice control that shows only `Battle` and `Both` potions, preserves inventory indexes, aligns cards, and disables Use outside the player turn.
* Added one shared context-eligibility helper and one shared confirmation modal using the existing Modal, Button, PotionIcon, potion translation helpers, and language font classes.
* Added exact English and Japanese Use, question, description subtitle, Yes, and No copy with English fallback.
* Confirming removes only the selected potion instance through the existing game setup context; cancelling leaves inventory unchanged.
* No potion effects, Mini trigger UI, routes, reward behavior, inventory capacity, replacement logic, dice logic, movement logic, dependencies, or unrelated styling/refactors were added.

Related Feature

* EPIC-011 Feature-005: Replace potion data with revamped source-of-truth potion table
* EPIC-011 Bug-012: Update Bridge Builder, Good Decisions, and Cave Runner potion availability to Mini

Goal

* Start implementing potion usage by adding the places where potions can be triggered.
* Add trigger UI for:

  * Board potions from the gameplay board UI.
  * Battle potions from the battle UI.
  * Both potions from both board and battle contexts.
* Add a shared confirmation modal that appears whenever a potion is triggered.
* Remove the potion from the player’s potion slots after confirmed use.
* Do not implement the actual potion effects yet.

Scope

* Add Board potion Use buttons in gameplay UI.
* Add Battle potion section above the battle dice roll.
* Add Battle potion Use buttons.
* Add shared potion-use confirmation modal.
* Remove confirmed potion from the player’s potion slots.
* Support English and Japanese confirmation text.
* Show potion description in the confirmation modal.
* Preserve layout alignment for potion slots with and without buttons.
* Keep Mini potion usage out of scope.

Potion Availability Rules

* Potion availability now controls where the potion can be triggered.
* Supported values are:

```txt id="is5g21"
Board
Battle
Both
Mini
```

* `Board` potions can only be triggered from the gameplay board UI.
* `Battle` potions can only be triggered from the battle UI.
* `Both` potions can be triggered from either the gameplay board UI or the battle UI.
* `Mini` potions are out of scope for this feature.
* Mini potions should not appear in the battle potion section.
* Mini potions should appear in the board potion slots if the player owns them, but they should not have a Use button.

Shared Potion Trigger Confirmation Modal

* Whenever a potion is triggered from anywhere, show a confirmation modal.
* This modal appears before the potion is consumed.
* English question:

```txt id="p5fwff"

```

* Japanese question:

```txt id="crbmqw"

```

* `X` should be replaced with the potion name in the current language.
* English should use the English potion name.
* Japanese should use the Japanese potion name.

Confirmation Modal Text Requirements

* The main question must use the `larger-text` class.
* The modal should use:

  * wooden modal background.
  * yellow text.
  * correct language font.
  * bottom-centred buttons.
  * buttons that are not full width.
* The confirmation modal is a text-focused modal, so the question should be placed in a `<p>` with `larger-text`.

Suggested structure:

  * do not trigger any effect.
* If the player chooses Yes:

  * remove the potion from the player’s potion slots.
  * close the modal.
  * do not trigger the potion effect yet, because potion effects are out of scope for this feature.

Feature-002: Add one-potion-per-turn limits and Active Potion gameplay section

Status

* done

Completion Notes

* Added a per-player Board-turn usage flag that is set only after confirmation and resets only when that player later begins a new Board turn.
* Added a per-battle player-turn usage flag that is set only after confirmation, stays locked through the enemy turn, and resets when Battle returns to the player through either normal advancement or a failed enemy freeze check.
* Enforced availability, actor, turn, and usage locks in the shared consumption action as well as disabling the existing Board and Battle Use buttons.
* Kept Board and Battle usage independent; entering Battle does not change the Board flag, and Battle usage does not change Board state.
* Added normalized `activePotion` player state and a hidden-by-default Active Potion section beneath Potions using the existing PotionIcon, translated name, and language font classes.
* Used the feature-specified darker brown Active Potion background and kept all new potion markup free of `ul` and `li`.
* Active Potion is display-only in this feature because later potion-specific features define which potion becomes active and when; no potion effects, Mini triggers, routes, reward logic, inventory limits, or unrelated UI changes were added.

Related Feature

* Feature-001: Add potion trigger UI and confirmation flow for Board and Battle potions
* EPIC-011 Feature-005: Replace potion data with revamped source-of-truth potion table
* EPIC-011 Bug-012: Update Bridge Builder, Good Decisions, and Cave Runner potion availability to Mini

Goal

* Limit potion usage so players can only use one potion per relevant turn context.
* Add a new hidden-by-default Active Potion section beneath the current gameplay potion section.
* Keep board, battle, and future mini-game potion usage limits separate.
* Preserve the trigger and confirmation flow from Feature-001.
* Do not implement individual potion effects in this feature.

Scope

* Add one-potion-per-board-turn limit.
* Add one-potion-per-battle-turn limit.
* Keep board potion usage and battle potion usage independent.
* Add disabled state for unavailable potion Use buttons.
* Add Active Potion section to gameplay UI.
* Style Active Potion section in darker brown than the normal potion section.
* Show active potion using the potion component with name included.
* Hide Active Potion section when empty.
* Preserve Mini potion implementation for later features.

Potion Usage Limit Summary

```txt id="48f81g"
Board: 1 potion per board turn.
Battle: 1 potion per battle turn.
Mini: not implemented yet.
```

* These limits are separate.
* Using a board potion should not disable battle potions.
* Using a battle potion should not disable board potions on a future board turn.
* Mini-game potion limits will be handled later.

Board Potion Limit Requirement

* A player can use only one board-usable potion per board turn.
* Board-usable potions are:

  * `Board`
  * `Both`
* Once the player successfully uses one board potion:

  * all other board potion Use buttons should become disabled for the rest of that board turn.
* This should include:

  * other `Board` potions.
  * other `Both` potions shown in the board UI.
* Potions that are not board-usable should still be displayed without active Use buttons, as defined in Feature-001.

Board Limit Reset Requirement

* The board potion usage limit should reset when that player’s next board turn begins.
* It should not reset merely because a modal opens or closes.
* It should not reset because the player enters a battle during the same board turn.
* It should reset when the turn properly advances and later returns to that player.

Battle Potion Limit Requirement

* A player can use only one battle-usable potion per battle turn.
* Battle-usable potions are:

  * `Battle`
  * `Both`
* Once the player successfully uses one battle potion:

  * all other battle potion Use buttons should become disabled until the next battle turn.
* This should include:

  * other `Battle` potions.
  * other `Both` potions shown in the battle UI.
* Battle potion buttons should also remain unavailable during enemy/opponent turns.

Battle Limit Reset Requirement

* The battle potion usage limit should reset on the player’s next battle turn.
* If the battle alternates between player and enemy/opponent turns:

  * using a potion on the player’s battle turn disables further battle potion use for that turn only.
  * on the player’s next battle turn, battle potion use becomes available again.
* Do not reset the battle potion limit during the same battle turn.

Board And Battle Independence Requirement

* Board and battle potion usage limits must be independent.
* If a player uses a potion on the board and then encounters a battle in the same turn:

  * battle potions should still be available in the battle.
  * battle potion usage should follow battle rules.
  * the player can still use one battle potion on their battle turn.
* Using a board potion should not disable battle potion buttons.
* Using a battle potion should not retroactively disable board potion logic except through normal turn progression.

Example

```txt id="bbjoi7"
Player uses Smokescreen on the board.
Board potion use is now locked for the rest of that board turn.

The player then enters a battle during the same turn.
Battle potion use is still available.
The player may use one Battle or Both potion during their battle turn.
```

Mini Potion Requirement

* Mini potion use limits are not implemented in this feature.
* Mini potions remain out of scope.
* Do not add Mini potion buttons.
* Do not add Mini potion trigger logic.
* Do not let the board potion limit or battle potion limit accidentally consume Mini potion state.
* Future mini-game potion features may add their own usage limit.

Potion Confirmation Interaction

* A potion should count as used only after the player confirms Yes in the use confirmation modal.
* If the player clicks Use and then chooses No:

  * do not remove the potion.
  * do not mark a potion as used for that context.
  * do not disable other potions.
* If the player clicks Use and then chooses Yes:

  * remove or move the potion according to the relevant implementation.
  * mark the relevant context as having used a potion this turn.
  * disable the remaining potion buttons for that context.

Disabled Button Requirement

* Once a potion has been used in the relevant context, remaining Use buttons should become disabled.
* Disabled buttons should remain visually clear.
* They should not open the confirmation modal.
* They should not consume a potion.
* They should not apply any future potion effect.
* Use the existing Button disabled styling where possible.

Suggested State Direction

```js id="v9q7wy"
player.turnPotionUsage = {
  boardPotionUsedThisTurn: false,
  battlePotionUsedThisBattleTurn: false
};
```

* Exact state shape can vary.
* The important requirement is that board and battle usage are tracked separately.

Suggested Helper Direction

```js id="gak71o"
function canTriggerPotion({ potion, context, usageState, isPlayerBattleTurn }) {
  if (context === "board") {
    return canUsePotionInContext(potion, "board") && !usageState.boardPotionUsedThisTurn;
  }

  if (context === "battle") {
    return (
      canUsePotionInContext(potion, "battle") &&
      isPlayerBattleTurn &&
      !usageState.battlePotionUsedThisBattleTurn
    );
  }

  return false;
}
```

* Exact implementation can vary.
* Reuse the context availability helper from Feature-001 where possible.

  * Japanese: `発動中のポーション`

* As soon as there is one potion in the active potion state, the section should become visible.
* Doing anything else with this section is out of scope.

Active Potion Visibility Requirement

* If there is no active potion:

  * do not reserve awkward empty space unless needed for existing layout stability.
* If there is an active potion:

* The section should support English and Japanese potion names through the existing potion component.

* Potions should also normally be consumed once they have been moved to the Active Potion section.
* Special exceptions can be defined by later potion-specific features.

  * using a potion should remove it from the player’s potion slots.
  * moving a potion to Active Potion should also remove it from the player’s potion slots.

Both Potion Requirement

* `Both` potions follow the limit of the context they are used in.
* If used from the board:

  * it counts as the player’s one board potion for that board turn.
  * it does not count as the player’s battle potion.
* If used from battle:

  * it counts as the player’s one battle potion for that battle turn.
  * it does not count as the player’s board potion.

* Battle potion cards should remain aligned after buttons become disabled.
* Disabled buttons should still occupy the same space as enabled buttons.
* The Active Potion section should not break the existing gameplay UI layout.

  * player gains a token and sees `New`.
  * player later removes or assigns all tokens from the token bag.
  * token bag count becomes 0.
  * `New` notification disappears.

Clear When Spells Modal Opens

* When the player opens the Spells modal, the notification should be removed.
* This represents the player seeing the new tokens in the token bag.
* The notification should clear as soon as the modal is opened.
* The player does not need to save, commit, or move tokens for the notification to clear.
* If the player opens the modal and then cancels/closes it, the notification should remain cleared unless a new token is added later.

Important Distinction

* The notification is not simply “token bag has tokens”.
* It means “new tokens have been added and the player has not opened the Spells modal since then”.
* However, the notification must also never show if the token bag is empty.

Suggested State Direction

```js id="e08itz"
player.hasUnseenTokenBagTokens = true;
```

* Set this to `true` when a token is added to the token bag.
* Set this to `false` when the player opens the Spells modal.
* Also force the badge hidden when token bag length is `0`.

Suggested Visibility Check

```js id="almgzb"
const showSpellsNewBadge =
  player.hasUnseenTokenBagTokens && player.tokenBag.length > 0;
```

* Exact implementation can vary.
* The important requirement is that both clear conditions are respected.

Expected Behaviour

* The Spells button no longer shows `!`.
* The Spells button shows `New` in English.
* The Spells button shows `新規` in Japanese.
