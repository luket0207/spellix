Feature-001: Add death token punishment and respawn result screen

Status

* done

Completion Notes

* Completed the first foundation slice by marking only the seven newly created starting tokens with `source: 'starting'` and `protected: true`; existing clone, draft movement, and commitment paths preserve this metadata.
* Added `DEATH_TOKEN_PENALTIES` and `getDeathTokenPenalty` for level 1-4 battle losses and future mini game deaths.
* Added a pure `applyDeathTokenPenalty` helper that considers only committed, unprotected spell-slot tokens, removes Black tokens first, randomly selects any remainder per individual token, never exceeds availability, and returns separate token copies with one-based column numbers plus immutable updated spell slots.
* Protection is metadata-based rather than colour-based, so later-gained Red and Blue tokens remain removable.
* Both automatic and debug battle losses now use one idempotent context transition that applies the level penalty once, persists the updated spell slots on the dying player, and stores `activeBattle.deathPenalty` with required `removalCount` and `removedTokens` fields.
* Added a feature-local `DeathResult` renderer that lists every removed token separately with its one-based spell column or shows the required no-removal explanation.
* Reused the existing locked battle-loss modal and respawn action, so the player remains dead until pressing Respawn, then returns to the existing first Start Area position at full health with removed tokens still absent and turn flow advanced.
* Existing battle win/reward behavior, damage, token bag contents, mini game UI, board generation, and unrelated battle behavior remain unchanged.

Goal

* Add a punishment flow for when a player dies.
* When a player dies in battle or in a future mini game, they should lose a number of removable tokens.
* Starting tokens can never be removed.
* Black tokens should always be removed first.
* Any remaining token removals should be random.
* Before the player respawns, show a new screen explaining exactly which tokens were removed.
* After confirming the result screen, respawn the player in the starting zone with full health and without the removed tokens.

Scope

* Add death punishment logic.
* Add token removal rules.
* Add a death result / punishment screen.
* Connect battle loss flow to the new punishment screen before respawn.
* Prepare the same punishment logic for future mini game deaths.
* Preserve existing battle win flow.
* Preserve existing battle loss detection.
* Preserve existing respawn behaviour after the punishment screen is completed.

Punishment Amount Requirement

* The number of tokens removed depends on how the player died.

```txt id="e4nd9x"

Loses level 2 battle = remove 1 token
Loses level 3 battle = remove 2 tokens
Loses level 4 battle = remove 3 tokens
Dies in mini game = remove 1 token
```

* Mini games are not implemented yet.
* For now, record mini game death as the same punishment level as a level 1 battle loss.
* Add a reusable helper or data map so future mini games can call the same punishment flow later.

Starting Token Protection Requirement

* Starting tokens can never be removed.
* Starting tokens are the original tokens placed during first spell setup:

* These tokens must be permanently protected from death punishment.
* The implementation should clearly distinguish starting tokens from gained tokens.
* Do not rely only on token colour to identify starting tokens.
* For example, a Red token gained later should be removable.
* A Blue token gained later should be removable.
* Starting Red and starting Blue tokens should not be removable.
* Add token metadata if needed.

```js id="qpglf1"
  type: "Red",
  source: "starting",
  protected: true
}
```

* Exact structure can vary.
* The important rule is that original starting tokens are protected, but later gained Red/Blue tokens are not automatically protected.

Removable Token Pool Requirement

* The death punishment should remove only removable tokens.
* Removable tokens are tokens that:

  * belong to the dying player.
  * are not protected starting tokens.
  * are currently committed in spell slots.
* Token pouch removal is out of scope unless the current project already treats the pouch as part of the same removable owned-token pool.
* If token pouch removal is already simple and consistent, it may be included, but the result screen must still clearly identify where the token was removed from.
* The core required display is for spell table columns.

Black Token Priority Requirement

* Black tokens are always removed first.
* Black token removal ignores the normal random selection rule.
* If the player has Black tokens that are removable, remove those before any other token type.

  * remove all removable Black tokens first.
  * then remove the remaining amount randomly from other removable tokens.
* Example:

  * Player loses a level 4 battle.
  * 3 tokens should be removed.
  * Player has 2 removable Black tokens.
  * Remove both Black tokens first.
  * Remove 1 additional removable token at random.
* If the player has enough Black tokens to satisfy the whole punishment:

  * remove only Black tokens.
  * do not randomly remove anything else.

Random Token Removal Requirement

* After removable Black tokens have been removed, all other removals should be completely random.
* Random removal should select from all remaining removable non-starting tokens.
* Each individual token should be eligible separately.
* If two Green tokens are in the same spell column, each Green token should be treated as its own removable token.
* Do not consolidate removal during calculation.
* Do not remove more tokens than are available.
* If there are not enough removable tokens, remove as many as possible.
* If there are no removable tokens, remove none.

Feature-003: Add battle reward generation and reward assignment flow

Status

* done

Completion Notes

* Added a feature-local battle reward configuration for levels 1-4 with the exact required choice counts and Common Token, Rare Token, Common Potion, and Rare Potion weights.
* Added a pure weighted category generator that rolls every choice independently, accepts an injected random function for deterministic tests, excludes zero-weight categories, and returns no choices for unsupported levels.
* Added exact-item selection for all four categories using only centralized token and potion rarity data. The normalized result is `{ category, itemType, item }`; token items include `type`, `label`, and `rarity`, while potion items preserve their catalog fields in an independent copy.
* Added complete battle reward choice generation with stable per-battle choice IDs. Category rolls are completed before exact items are selected, and the configured level choice count is preserved.
* Both automatic combat wins and the existing debug Win transition now generate and store `activeBattle.rewardChoices` once. Repeated reward transitions reuse the stored choices, while battle losses generate no rewards.
* Updated the existing reward page with a plain Part 1 choice list that shows every generated category and exact token or potion. Selecting a choice stores its ID in battle state, moves the page to the assignment step, and cannot be changed by a later selection attempt.
* Removed the placeholder Continue action while a reward is unresolved, so neither debug nor automatic wins can clear the battle or advance the turn before assignment.
* Added the first token assignment paths using the existing token creation and token-bag capacity helpers. A selected token can be added to a bag with space or discarded, and the stored `rewardResolution` prevents either action from applying more than once.
* A full token bag cannot receive a sixth token and displays a plain full-capacity message. Each current bag token is now an individual replacement choice; selecting one reuses the existing immutable replacement helper, keeps the bag at five, stores the replaced token ID in `rewardResolution`, and cannot apply twice.
* Continue becomes available only after the token is added, replaced, or discarded; it then clears the battle, advances the turn, and returns to gameplay.
* Added direct spell-slot assignment using the existing read-only committed spell display. All six slots are shown with plain Select controls, full five-token slots are disabled, and the chosen slot requires a separate Confirm action before state changes.
* Confirming creates one unique committed reward token directly in the selected slot, records the slot ID in `rewardResolution`, prevents later duplicate or alternate resolution, and then enables the existing Continue flow.
* Selecting a potion reward now reuses the existing three-potion capacity helper. Below capacity, the potion is added immediately to the winning player, a `potionSlot` resolution is stored, repeated selection cannot duplicate it, and Continue becomes available.
* At full potion capacity, the reward choice locks without adding a fourth potion and shows a plain full-capacity message. Each current potion has a replacement action, and the new potion can be discarded separately.
* Full-capacity replacement reuses the existing immutable pending-potion resolver, keeps exactly three potions, and stores a `potionSlotReplacement` resolution. Discarding the new potion leaves the collection unchanged and stores a `potionDiscarded` resolution; both paths apply only once and enable Continue.
* Completed mixed reward regression across token and potion choices. The selected reward is the only item applied, resolved rewards survive navigation back to gameplay, the battle clears, and the turn advances once.
* Stabilized the BattlePage reward regression by deterministically generating a token for its intentionally unresolved assignment assertion; potion auto-resolution remains covered separately on the RewardPage.
