Feature-002: Add ordered Cave Game reward resolution flow after loot chest selection

Status

* done

Completion Notes

* Added an explicit Cave reward resolution state with `lootChest`, `tokenAssignment`, `potionResolution`, and `finalTurnBehaviour` stages plus source-preserving token and potion queues.
* Cave retreat now defers all token and potion inventory changes, opens Loot Chest first when present, assigns every pending token next, resolves pending potions one at a time, and only then applies the stored turn behaviour.
* Loot Chest token and potion rewards join the same Cave queue without replacing Cave rewards; Loot tokens retain first-token assignment order while all token work still completes before either source's potion work.
* Reused the existing Spell Token Assignment controls for spell slots, token bag, replacement, and discard, including sequential assignment when both Loot and Cave provide tokens.
* Reused the existing potion capacity and replacement/discard logic. Available potions now show the required translated confirmation before continuing, while full slots require a replacement or discard choice for each queued potion.
* Reused `MagicalNightSky`, the wooden modal classes, global `Button`, `PotionIcon`, existing English/Japanese reward text, and established language font classes on the potion confirmation and full-capacity states.
* Final return is blocked until the queue is empty. Roll Again preserves the active player and notice; no Roll Again advances to the next player through the global next-turn modal invariant.
* River Loot Chest behavior, reward probabilities, reward types, routes, dependencies, and unrelated inventory behavior were not changed.
* No `ul` or `li` elements were introduced.

Related Feature

* EPIC-011 Feature-001: Implement Loot Chest page with hidden reward choices, chest shuffle animation, and reward assignment flow
* EPIC-010 Feature-012: Add Cave Mini Game reward generation, retreat reward handling, loot routing, and roll-again preservation
* EPIC-010 Feature-014: Grant Cave Game token and potion rewards, handle full bags/slots, and add Cave reward debug buttons
* EPIC-010 Feature-015: Redesign Spell Token Assignment as a generic modal-based reward assignment screen
* EPIC-010 Bug-005: Next-turn modal must always appear after any player turn change

Goal

* Add a strict reward handling order after the Cave Game.
* Ensure all Cave Game rewards and Loot Chest rewards are resolved in a predictable sequence.
* Prevent tokens, potions, loot chest rewards, or roll-again turn behaviour from being lost.
* Make the reward resolution flow consistent and easy to extend later.

Required Reward Resolution Order

* After the Cave Game, rewards must be handled in this exact order:

```txt id="t6cs2h"
1. Resolve Loot Chest if one was found.
2. Assign all pending tokens.
3. Resolve all pending potions.
4. Apply final turn behaviour.
```

* Do not apply final turn behaviour until all rewards have been resolved.
* Do not return fully to normal board control until this sequence is complete.

Step 1: Loot Chest Resolution

* If the player found a loot chest in the Cave Game:

  * send the player to the Loot Chest page first.
  * resolve the Loot Chest reward using EPIC-011 Feature-001.

* This must happen before assigning any Cave Game token rewards.

* If the Loot Chest reward is a token, add it to the pending token rewards queue.

* If the Loot Chest reward is a potion, add it to the pending potion rewards queue.

* If the Loot Chest reward is Nothing, add nothing.

* After the Loot Chest page finishes, continue to token assignment.

* If the player did not find a loot chest:

  * skip this step.
  * go directly to token assignment.

Step 2: Token Assignment

* After Loot Chest resolution is complete, assign any pending tokens.
* Pending tokens may come from:

  * the Cave Game itself.
  * the Loot Chest reward.
  * both.
* All pending tokens must be handled through the existing Spell Token Assignment component.
* Do not automatically place Cave Game tokens into the token bag.
* Do not silently discard pending tokens.
* If there are multiple pending tokens, they must all be assigned or discarded before continuing.

Token Assignment Options

* Each pending token should be assignable to:

  * a valid spell slot.
  * the token bag.
  * trash/discard.
* Use the generic Spell Token Assignment styling from EPIC-010 Feature-015.
* Use the animated night sky background.
* Use the wooden modal-style assignment container.
* Do not use `ul` or `li`.

Multiple Token Requirement

* If the Cave Game produced a token and the Loot Chest also produced a token:

  * both tokens must be handled.
* Preferred behaviour:

  * show both pending tokens in one Spell Token Assignment flow.
* Acceptable fallback:

  * queue the tokens and show the assignment flow once per token.
* In either case:

  * no token should be lost.
  * final reward handling must wait until all pending tokens are resolved.

Step 3: Potion Resolution

* After all pending tokens have been assigned or discarded, resolve pending potions.
* Pending potions may come from:

  * the Cave Game itself.
  * the Loot Chest reward.

  * a White token in one column.
  * a White token in an adjacent column.
  * the two columns are not already merged together.
  * the player has fewer than 2 successful merges.
* If more than one possible merge is present, handle one at a time or apply a clear deterministic rule.
* Avoid accidentally merging non-adjacent columns.
* Avoid merging the same column into multiple separate groups unless explicitly supported later.

Merge Confirmation Requirement

* When a valid merge is detected during commit, show a different confirmation alert instead of the normal commit confirmation.
* English:


  * wooden modal background.
  * yellow text.
  * correct English/Japanese font.
  * bottom-centred buttons.
* This is a text-only confirmation modal, so the main `<p>` tag should use `larger-text`.

Merge Token Loss Rule

* When two columns are merged, one column loses its tokens.
* Decide which column loses tokens using this priority order:

```txt id="8uj0c5"
1. The column with the fewest total tokens loses its tokens.
2. If both columns have the same number of total tokens, the column with the fewest rare tokens loses its tokens.
3. If both columns are still tied, choose one of the two columns at random.
```

* The losing column loses all tokens in that column.
* The retained column keeps its tokens.
* The two columns then act as one merged column from that point onward.

Rare Token Count Requirement

* For the merge loss tie-breaker, count rare tokens in each candidate column.
* Rare tokens should use existing token rarity data.
* If rarity is missing, treat the token as common unless existing project logic says otherwise.
* Only committed tokens in the two merge candidate columns should be counted.

Merge Confirmation Example

* If columns 3 and 4 are being merged:

  * compare total token counts in column 3 and column 4.
  * if one has fewer tokens, that column is the losing column.
  * if totals are equal, compare rare-token counts.
  * if still equal, choose one randomly.

```txt id="umysri"
Committing this change will merge columns 3 and 4. This means you will lose the tokens from column 4. Is this ok?
```

Merged Column Battle Requirement

* Once two columns are merged, they act as one column in battle.
* If either column number is rolled, the whole merged column is triggered.
* Example:

  * columns 3 and 4 are merged.
  * the retained merged token set contains 2 Red tokens.
  * if battle roll is 3, the merged column triggers and deals 20 damage.
  * if battle roll is 4, the same merged column triggers and deals 20 damage.
* The roll number should still visually/semantically correspond to the rolled number, but the effects should use the merged column’s combined active token set.
* Do not double-trigger the merged column if the roll maps to either side.
* Merged columns should behave consistently for both player attacks and enemy/opponent matching logic where player spell columns are referenced.

Merged Column Storage Requirement

* Store merged-column state in a way battle logic can query.

```js id="evuimd"
function getEffectiveSpellColumn(player, rolledColumnNumber) {
  const merge = player.mergedColumns.find((merge) =>
    merge.columns.includes(rolledColumnNumber)
```

```js id="ceoes1"
function getColumnCapacity(player, columnIndex) {
```
