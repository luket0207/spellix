Feature-001: Implement Small Heal, Heal, and First Aid potion behaviour

Test Status

* passed

Manual Regression Steps And Expected Results

1. Set a player to 40 / 115 HP through three committed Light Green tokens, use Small Heal on the Board, and confirm.
   Expected: Health becomes 75 / 115, Small Heal is consumed, the Board potion limit locks, and no Active Potion appears.
2. Set a player to 25 / 110 HP, use Heal on the Board, and confirm.
   Expected: 60% of max health rounds from 66 to 65, producing 90 / 110 HP.
3. Set a player to 80 / 100 HP, use Heal, and confirm.
   Expected: Health clamps to 100 / 100 rather than exceeding max health.
4. Enter Battle at 40 / 115 HP, use First Aid, and confirm.
   Expected: 50% of max health rounds to 60, producing 100 / 115 HP; First Aid is consumed and does not enter Active Potion.
5. Inspect the animation after confirmed Board healing.
   Expected: A green Font Awesome flask starts at the centre of the top player image, grows to the image width, shakes three times, fades out, and lasts 1.5 seconds.
6. Repeat the animation check after confirmed Battle healing.
   Expected: The same animation appears over the battle player image and nowhere over the enemy image.
7. Try First Aid on the Board and use two eligible potions in one Board or Battle turn.
   Expected: Existing availability and one-potion-per-turn rules remain unchanged.
8. Inspect the browser console throughout.
   Expected: No console errors occur.

Automated Tests Completed

* Red-first execution produced 12 intended failures across healing calculations, state updates, consumption, and Board/Battle animation placement.
* The final focused regression passes 4 suites and 13 tests for 30%, 60%, and 50% healing, nearest-5 rounding, the documented 25/110 and 40/115 examples, max-health clamping, Light Green-adjusted max health, consumption, no Active Potion state, icon placement, and animation removal.
* The broader potion regression passes 11 suites and 68 relevant tests covering existing context availability, confirmation, inventory indexes, one-use limits, capacity, Board/Battle lists, and Active Potion behavior.
* Stylesheet assertions verify the green flask grows from zero to full image width, has three shake keyframes, fades to zero opacity, and uses a 1.5-second animation.
* `npm run build` compiles successfully after Create React App and ESLint checks.
* `git diff --check` reports no whitespace errors.

Automated Test Limitations

* The project has no `npm run lint` script; the production build supplied the available ESLint compile check.
* JSDOM verifies health state, DOM placement, icon identity, classes, animation lifecycle, and stylesheet declarations but cannot visually inspect real-browser animation smoothness, exact image-width matching, rendered colour, or console output.

Manual Testing Still Needed

Feature-002: Implement Roll Choice potion behaviour

Test Status

* passed

Manual Regression Steps And Expected Results

1. Give the current player Roll Choice on the Board, click Use, and accept the normal confirmation.
   Expected: A wooden Roll Choice modal asks `What do you want the next roll of the dice to be?`; the potion remains in its slot and Board potion usage is not yet locked.
2. Inspect and use the six number controls.
   Expected: Six equal global buttons appear in two rows of three, labelled 1 through 6, with no `ul` or `li`.
3. Choose 4 from the Board modal.
   Expected: Roll Choice is consumed, Board potion usage locks, and Active Potion shows Roll Choice with a `4` over its potion icon in the English font.
4. Click Roll Dice.
   Expected: The dice result is 4 without random generation, normal movement choices use 4, and Roll Choice disappears from Active Potion when the result resolves.
5. Complete the turn and roll normally the next time that player is eligible.
   Expected: The stored forced value is gone and the dice returns to normal random generation.
6. Give the battle player Roll Choice, accept confirmation, and choose 2.
   Expected: Roll Choice is consumed after selection, Battle potion usage locks, the next player Battle roll is 2, and no Board Active Potion state is created.
7. Repeat the selection flow with each value from 1 through 6 and with an English and Japanese player.
   Expected: Every selected value is stored and used exactly once; both questions use the correct text and language font.
8. Inspect both flows and the browser console.
   Expected: Existing confirmation, turn restrictions, dice animation, movement, and battle resolution continue normally with no console errors.

Automated Tests Completed

* Red-first execution failed all 7 focused suites because delayed consumption, the choice modal, translations, stored forced state, numbered Active Potion, and non-immediate forced dice input did not exist.
* The final focused regression passes 7 suites and 16 tests, including every choice from 1 through 6, no-choice non-consumption, Board/Battle state differences, exact English/Japanese questions, two-row grid declarations, one-shot clearing, Board and Battle forced results, and return to random rolling.
* The broader regression passes 16 suites and 88 relevant tests across potion capacity, duplicate indexes, context availability, confirmation, one-use limits, healing, Active Potion, player creation/normalization, PotionIcon, translations, and Board/Battle integration.
* The legacy duplicate-capacity fixture now uses Small Heal instead of bypassing Roll Choice selection; its duplicate-index behavior remains unchanged and passing.
* `npm run build` compiles successfully after Create React App and ESLint checks.
* `git diff --check` reports no whitespace errors.

Automated Test Limitations

* The project has no `npm run lint` script; the production build supplied the available ESLint compile check.
* JSDOM verifies state, exact copy, controls, classes, DOM placement, forced results, random-call behavior, and CSS grid declarations but cannot visually inspect the wooden background, yellow text, real-browser button sizing, or console output.

Manual Testing Still Needed

* Run the eight-step browser regression above to visually confirm both localized modal layouts, Active Potion number placement, live dice timing, and console output.
