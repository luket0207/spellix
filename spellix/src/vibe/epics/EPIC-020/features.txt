Feature-001: Make gameplay layout scale to fit screen height

Status

* done

Related Feature(s)

* EPIC-004 Feature-004: Board generation
* EPIC-004 Feature-005: Board movement and dice movement
* EPIC-016 Feature-002: Multi-square board features landing/movement/highlighting
* EPIC-018 Feature-006: Prevent white flash when returning to gameplay page
* EPIC-020 Feature-016: Show environment or feature name when hovering highlighted movement squares

Goal

* Make the gameplay page responsive across different desktop and laptop resolutions.
* This does not need to make the game properly playable on mobile.
* The important requirement is that the board, player UI, potion UI, spell display, and modal layer fit within the visible height of the screen.
* The same scale should be maintained throughout the app so modals and overlay content do not feel mismatched from the board.

Problem Summary

* On some resolutions, the full gameplay page does not fit on screen.
* The board and surrounding gameplay UI can overflow vertically.
* This makes the player scroll or lose access to important UI.
* Modals can also appear too large relative to the visible screen.

Required Behaviour

* The gameplay page must always fit within the viewport height.
* The board should scale down when vertical space is limited.
* The gameplay UI should scale down with the board.
* Modal pages and overlay panels should scale consistently with the board/gameplay shell.
* Scaling should preserve:

  * board aspect ratio.
  * square alignment.
  * player position alignment.
  * movement highlight alignment.
  * drag-and-drop token alignment.
  * hover label positioning.
  * modal proportions.

Desktop-First Responsive Requirement

* This is not a mobile redesign.
* The game does not need to become touch-optimised or phone-friendly.
* The target is desktop/laptop screens with different heights.
* Avoid designing around a narrow mobile portrait layout.
* Maintain the existing visual style and composition.

Base Layout Requirement

* Define one base gameplay design size.
* The current board is 31 x 31 squares.
* If the current square size is 30px, the unscaled board size is:

```txt id="z0870m"
930px x 930px
```

* The full gameplay shell should account for:

  * top player/turn UI.
  * dice controls.
  * potion sections.
  * active potion section.
  * committed spell slot display.
  * board.
  * any required spacing around those elements.

Suggested Scaling Direction

* Use a wrapper around the full gameplay page content.
* Calculate a scale based on available viewport height.
* Apply the scale to the gameplay shell.
* Keep the wrapper centred horizontally.

Suggested CSS direction:

```css id="l7z982"
.gameplay-page {
  min-height: 100vh;
  overflow: hidden;
  display: flex;
  justify-content: center;
  align-items: flex-start;
}

.gameplay-scale-root {
  --gameplay-base-height: 1120px;
  --game-scale: min(1, calc((100vh - 24px) / var(--gameplay-base-height)));

  transform: scale(var(--game-scale));
  transform-origin: top center;
}
```

* Use the real base height after measuring the current layout.
* Do not hard-code a guessed value if the project already has a better layout container.
* If the board and UI need separate scaling, prefer one shared CSS variable rather than independent scale calculations.

Board Scaling Requirement

* The board should remain square.
* Each square should remain visually consistent.
* Player pieces should remain aligned to squares.
* Multi-square features should keep correct dimensions.
* Internal feature footprint logic should not change.
* Movement highlight overlays must scale with the board.

Suggested direction:

```css id="thtijb"
.board-wrapper {
  width: calc(930px * var(--game-scale));
  height: calc(930px * var(--game-scale));
}
```

Alternative:

```css id="qefgt2"
.board-and-ui-shell {
  transform: scale(var(--game-scale));
  transform-origin: top center;
}
```

* Use whichever approach preserves existing coordinate calculations best.
* If the board already uses absolute coordinates, wrapping with `transform: scale()` may be safer than recalculating every square size.

Modal Scaling Requirement

* Modal pages should not overflow the viewport height.
* Modals should use the same scale logic or be constrained relative to viewport height.
* For standard modal panels:

  * use `max-height`.
  * allow internal vertical scrolling only when content genuinely needs it.
* The modal background art should scale cleanly.

Suggested modal direction:

```css id="z18jwy"
.modal-background {
  max-height: calc(100vh - 48px);
  overflow-y: auto;
}
```

* Do not globally force `overflow-x: hidden` on every modal unless it is safe.
* Feature-015 separately scopes horizontal overflow fixing to the spells modal.

Full-App Consistency Requirement

* Maintain the same scale or sizing approach throughout:

  * gameplay.
  * battle.
  * hazard.
  * decision.
  * village.
  * cave.
  * river.
  * loot chest.
  * spell assignment.
  * settings rules modal.
* If some pages are separate routes, they should still use the same starry background and responsive modal sizing.

Interaction Requirement

* Scaling must not break:

  * board square click detection.
  * valid move calculation.
  * hover detection.
  * token drag-and-drop.
  * potion tooltips.
  * token tooltips.
  * board debug tools if debug mode is enabled.

Suggested Implementation Steps

* Identify the highest-level gameplay container.
* Measure current natural gameplay height.
* Add a scale variable based on `window.innerHeight` or CSS viewport units.
* Prefer CSS-only scaling if possible.
* If React state is needed, debounce resize handling.
* Apply the same scale to board, board overlays, and UI panels.
* Audit modal pages and adjust max-height/internal scrolling.
* Test hover/click/drag after scaling.

Out Of Scope

* No mobile redesign.
* No change to board dimensions or number of squares.
* No change to movement logic.
* No change to procedural generation.
* No new mobile controls.
* No zoom buttons.
* No browser fullscreen requirement.

Testing Checkpoints

* Test on a large desktop screen.
* Test on a shorter laptop screen.
* Test with browser dev tools at several viewport heights.
* Confirm the whole gameplay layout fits within the screen height.
* Confirm the board remains square.
* Confirm no important UI is cut off.
* Confirm no vertical page scroll is required during normal gameplay.
* Confirm modals fit the screen or scroll internally.
* Confirm token drag-and-drop still works after scaling.
* Confirm movement highlights still align with board squares.
* Confirm hover labels from Feature-016 still align with the board.
* Confirm battle page remains usable.
* Confirm village page remains usable.
* Confirm rules/settings modal remains usable.
* Confirm there are no console errors.
* Update `implementation.txt` and `testing.txt` before marking this feature done.

Implementation Notes

* Measured the existing natural gameplay footprint as 1320px wide by 940px high: the 940px board footprint, 20px column gap, and 360px sidebar footprint.
* Added one centred gameplay viewport and one transformed scale root around the board and sidebar so the board, player UI, dice controls, potion UI, active potion UI, and committed spells all use the same scale.
* The scale uses the smaller of the available viewport-height and viewport-width ratios, preserves the original size on larger screens, reserves a 12px inset on every side, and updates through a 50ms debounced resize listener.
* Kept the board at 31 by 31 squares with its existing 30px square size and did not change board generation, movement, click handling, feature footprints, highlights, player positioning, or hover coordinate logic.
* Kept gameplay modals outside the transformed board shell so fixed overlays and drag-and-drop coordinates remain stable.
* Added dynamic viewport-height constraints and internal scrolling support to the shared standard modal panel while retaining `vh` fallbacks for browsers without `dvh` support.
* Updated the shared starry gameplay page height to use the dynamic viewport with its existing fallback, preventing the responsive shell from creating normal page scrolling.
* Battle, Village, Rules, Settings, and other separate flows retain their existing composition and benefit from the shared viewport-constrained modal behavior; no route, mechanics, mobile redesign, zoom controls, or unrelated styling was added.
* Per the main project rules, only `features.txt` and `testing.txt` are used for this feature; `implementation.txt` was not created or changed despite the stale checkpoint text above.

Feature-005: Show final hit, death icon, and complete animations before battle ends

Status

* done

Related Feature(s)

* EPIC-014 Feature-006: Battle dice result visible before animations
* EPIC-017 Bug-001: Guard shield should appear before counter damage removes it
* EPIC-017 Bug-003: Guard shield should remain visible until removed by damage or turn end
* EPIC-015 Feature-007: Add death state in turn change modal before respawn

Goal

* Make the final hit of a battle visible.
* Currently, if damage kills a character, the battle can end too quickly.
* The player should see:

  * the final damage land.
  * health being removed.
  * any counters complete.
  * the defeated character reach 0 HP.
  * a grey skull icon animation.
  * then the battle ends.

Required Death Sequence

When a battle hit causes a character to reach `0 HP`, the flow should be:

```txt id="th6efv"
1. Dice result is shown.
2. Spell animations begin.
3. Damage/counter/guard/deflect/freeze animations complete their intended cycle.
4. Health is removed when damage hits, as normal.
5. If health reaches 0, show faSkullCrossbones over the defeated character.
6. The skull icon grows from the centre and shakes.
7. After the skull animation completes, the battle ends.
8. The normal win/loss flow begins.
```

Animation Completion Requirement

* Do not end the battle immediately when lethal damage is calculated.
* Do not skip queued counter damage if it should still happen.
* Do not skip guard/deflect visual resolution.
* Do not hide the battle UI before the final health bar update is visible.
* The battle should end only after the death visual has completed.

Counter Interaction Requirement

* If the killing attack also triggers counter damage:

  * the counter animation should still complete if it is part of the same battle resolution.
  * counter damage should still apply if rules say it applies.
  * if counter damage also kills the attacker, resolve this safely and visibly.
* If both characters reach 0 HP in the same exchange, avoid crashing.
* If the game has no draw rule, use existing battle winner logic, but still show both relevant health/death animations.

Health Requirement

* Health should be removed at the normal damage impact moment.
* The health bar must visibly reach `0`.
* The skull icon should appear only after the defeated character’s health is at 0.
* Do not show the skull before health is removed.

Skull Icon Requirement

* Use Font Awesome:

```txt id="ld4oza"
faSkullCrossbones
```

* Colour:

```txt id="cx045y"
grey
```

* The icon should:

  * appear over the defeated character image.
  * be centred over the character.
  * grow from the centre.
  * shake.
  * use the same animation style as the potion-applied icon animation.
  * complete before the battle result/loss/win flow begins.

Feature-007: Implement SOS potion

Status

* done

Related Feature(s)

* EPIC-012 Feature-003: Potion data source of truth
* EPIC-016 Feature-004: Implement village visits, village rewards, and village healing
* EPIC-020 Feature-010: Expand to 4 villages and update village reward rules
* EPIC-020 Feature-011: Add village action choice page

Goal

* Implement the SOS potion.
* SOS should immediately move the player to the nearest village.
* The normal village sequence should then play.
* The potion should be discarded.
* This consumes the player’s turn exactly like landing on a village.

Potion Type

* SOS is a Board potion.
* It should be available from the board potion UI.
* It should use the standard potion confirmation modal before activation.

Use Confirmation

* Use the existing standard potion confirmation flow.

English structure:

```txt id="jld74i"
Are you sure you want to use SOS?
```

Japanese structure:

```txt id="s8anqx"
SOSを使用してもよろしいですか？
```

* If the player selects No:

  * close confirmation.
  * do not consume SOS.
  * do not move the player.
  * board potion use should not be locked.
* If the player selects Yes:

  * consume SOS.
  * move the player to the nearest village.
  * begin village sequence.

Nearest Village Requirement

* Calculate the nearest village from the player’s current board position.
* Use orthogonal board distance.
* Do not count diagonal distance.
* Suggested distance:

```txt id="frlw5b"
distance = abs(playerX - villageX) + abs(playerY - villageY)
```

* If the player is on a multi-square feature or village footprint, use their logical position or nearest occupied/visual cell consistently with current board movement logic.
* If two or more villages are tied for nearest:

  * choose one randomly.

Village Destination Requirement

* SOS can move the player to any village currently generated on the board:

  * Field Village.
  * Forest Village.
* After Feature-010, there should be 4 villages.
* SOS should choose the nearest among all 4.

Movement Requirement

* No pathfinding animation is required.
* The player can immediately appear at the destination village.
* If the village is multi-square:

  * place the player using the current feature visual cell placement rules.
  * avoid overlapping another player if possible.
* The player's logical position becomes that village feature.

Village Sequence Requirement

* After teleporting, run the same logic as landing on that village normally.
* This means:

  * eligible village rewards from Feature-010 can trigger.
  * village action choice page from Feature-011 appears after rewards.
  * Rest/Wandsmith/Leave rules apply.
  * village action lock/reset rules apply.
  * turn ends according to the chosen village action.

Turn Requirement

* SOS takes up the player’s turn.
* The player should not roll/move after SOS.
* The turn should end only after the village sequence has fully resolved.
* If the player chooses Rest, Wandsmith, or Leave, follow that flow to turn end.

Active Potion Requirement

* SOS should not go into Active Potion.
* It resolves immediately.
* It is discarded once used.

Debug / Edge Case Requirements

* If no villages exist because of a generation error:

  * do not crash.
  * show a safe error modal or log developer warning.
  * do not consume SOS if no destination can be found.
* If the player is already on a village:

  * the nearest village may be the current village.
  * begin the village sequence normally.

Out Of Scope

* No teleport animation required.
* No player choice of village destination.
* No new village reward rules.
* No change to village generation except Feature-010.
* No change to other teleport effects.

Testing Checkpoints

* Give a player SOS.
* Use SOS from different positions on the board.
* Confirm confirmation modal appears.
* Click No and confirm SOS is not consumed.
* Click Yes and confirm SOS is consumed.
* Confirm player moves to nearest village.
* Place player equal distance from two villages.
* Confirm one tied village is chosen randomly.
* Confirm village sequence begins.
* Confirm village rewards trigger if eligible.
* Confirm village choice page appears after rewards.
* Confirm player turn ends after village action resolves.
* Confirm SOS does not appear in Active Potion.
* Confirm there are no console errors.
* Update `testing.txt` before marking this feature done.

Implementation Notes

* Added a pure nearest-village selector that dynamically considers every generated Field or Forest Village, measures orthogonal distance to each full village footprint, treats the player's current logical village as distance zero, and uses randomness only to resolve tied villages.
* Reused the standard Board potion confirmation and consumption flow. No leaves SOS and movement untouched; Yes discards it, records Board potion use, and never assigns it as Active Potion.
* Reused the existing multi-square visual placement helper so the teleported player keeps the village's logical feature identity, avoids occupied village cells when possible, records that Start has been left, and clears one-use Anywhere movement mode.
* Reused `startVillageVisit` and the existing `/village` navigation so current rewards, healing, turn completion, and later Feature-010/Feature-011 village extensions remain one shared sequence.
* A missing generated village logs a developer warning and closes confirmation without consuming SOS, moving the player, or locking Board potion use.
* Updated the centralized English and Japanese SOS descriptions to refer to the nearest village. Added no route, modal, animation, styling, generation rule, reward rule, or player destination choice.

Status

* done

Related Feature(s)

* EPIC-016 Feature-008: Trigger board events based on landed environment
* EPIC-011 Feature-001: Loot Chest page
* EPIC-020 Feature-010: Expand to 4 villages and update village reward rules

Goal

* Implement Metal Detector.
* When played, it should guarantee that the player finds loot on this turn if they land on a non-feature square.
* It should go into the Active Potion section for this turn only.
* After the turn resolves, it should be discarded.

Potion Type

* Metal Detector is a Board potion.
* It should use the standard Board potion use flow.
* It counts as the player’s one board potion for the turn.

Use Behaviour

* When the player confirms using Metal Detector:

  * remove it from potion slots.
  * place it in Active Potion.
  * mark `metalDetectorActive` for the current player/turn.
  * allow the player to roll and move as normal.

Active Potion Requirement

* Metal Detector should appear in the Active Potion section.
* It should remain visible until the landing event resolves.
* It should then be discarded/cleared.
* If Roll Again occurs before landing resolution ends, define carefully:

  * Metal Detector should apply to the first valid non-feature landing that resolves an event.
  * once it triggers Loot Chest or is discarded by a feature landing, it should no longer apply.

Landing Requirement

* After the player rolls and chooses a square:

  * check whether the destination is a feature.
* If the destination is not a feature:

  * skip normal environment event probability selection.
  * trigger the Loot Chest found flow.
  * run the normal Loot Chest sequence.
  * end the turn after Loot Chest completes.
  * discard Metal Detector.

Feature Exclusion

* Metal Detector should not override feature squares.
* If the player lands on:

  * Village
  * Elite Tower
  * Boss Battle
* then that feature’s normal logic happens.
* Metal Detector is discarded at the end of the turn after the feature sequence resolves.

Non-Feature Definition

* Non-feature squares include normal environments:

  * Field
  * Hills
  * Gravel
  * Mud
  * Stream
  * River
  * Woods
  * Forest
  * Mountains

* Features include:

  * Village
  * Elite Tower
  * Boss Battle
  * any future special multi-square feature.

Loot Chest Requirement

* Use the existing Loot Chest found modal if the game already has one.

English:

```txt id="pqr56z"
You found a Loot Chest!
```

Japanese:

```txt id="zbdot5"
戦利品の宝箱を見つけました！
```

Button:

```txt id="ypy1l5"
Open Chest / 宝箱を開ける
```

* Then run the existing Loot Chest sequence.
* After Loot Chest finishes, return to board and advance to next player.

Interaction With Smokescreen

* If Metal Detector and Smokescreen could somehow both be active, Metal Detector takes priority on non-feature landing because it replaces normal event selection with Loot Chest.
* This should be rare because only one board potion should normally be usable per board turn.

Out Of Scope

* No special loot rewards.
* No different chest visuals.
* No stacking multiple loot chests.
* No change to normal Loot Chest reward odds.
* No animation required.

Testing Checkpoints

* Use Metal Detector.
* Confirm it moves to Active Potion.
* Roll and land on Field.
* Confirm Loot Chest is guaranteed.
* Confirm normal Field event selection is skipped.
* Complete Loot Chest.
* Confirm turn advances.
* Confirm Metal Detector is discarded.
* Use Metal Detector and land on Village.
* Confirm Village sequence happens instead of Loot Chest.
* Confirm Metal Detector is discarded after the village sequence.
* Use Metal Detector and land on Elite Tower.
* Confirm Elite Tower battle happens.
* Confirm Metal Detector is discarded after the turn resolves.
* Confirm there are no console errors.
* Update `testing.txt` before marking this feature done.

Implementation Notes

* Reused the existing standard Board potion confirmation and consumption flow. No leaves Metal Detector in its slot and Board use unlocked; Yes removes it, marks Board use, and stores it in the existing `activePotion` field for the current turn.
* Used `activePotion.id === 'metal-detector'` as the `metalDetectorActive` marker instead of duplicating derived player state.
* Added the guaranteed Loot Chest branch only after Village, Elite Tower, Boss Battle, and other feature handling, but before debug event choice and random environment event selection.
* Reused the existing `boardLanding` Loot Chest event, localized found modal, Loot Chest page, reward assignment, return routing, and next-player transition without changing rewards or odds.
* Added Metal Detector to shared Board-turn potion expiration so it remains visible through Loot Chest or feature resolution and clears only when that turn advances.
* The existing one-Board-potion rule prevents normal Metal Detector/Smokescreen stacking. Metal Detector's landing branch precedes normal event selection, preserving its required priority if later effects also inspect non-feature landings.
* Added no component, route, modal, field, styling, animation, loot rule, or feature override.

Feature-009: Implement Smokescreen potion

Status

Related Feature(s)

* EPIC-012 Feature-003: Potion data source of truth
* EPIC-016 Feature-008: Trigger board events based on landed environment
* EPIC-020 Feature-008: Implement Metal Detector potion

Goal

* Implement Smokescreen.
* When played, it prevents the player from encountering random battles for this turn.
* It should go into the Active Potion section for this turn only.
* Other events should still be possible.

Potion Type

* Smokescreen is a Board potion.
* It should use the standard Board potion confirmation flow.
* It counts as the player’s one board potion for the turn.

Use Behaviour

* When the player confirms using Smokescreen:

  * remove it from potion slots.
  * place it in Active Potion.
  * mark `smokescreenActive` for the current player/turn.
  * allow the player to roll and move as normal.

Active Potion Requirement

* Smokescreen should appear in the Active Potion section.
* It should remain until the player’s landing event resolves.
* It should then be discarded.

Battle Prevention Requirement

* While Smokescreen is active, random environment event selection must exclude:

  * Level 1 Battle
  * Level 2 Battle
  * Level 3 Battle

* The remaining valid non-zero event chances should be reweighted proportionally.

* The player can still encounter:

  * Nothing
  * River Mini Game
  * Cave Mini Game
  * Decision
  * Hazard
  * Loot Chest
  * Roll Again
  * any other non-battle event for that environment.

Example: Field

* If Field normally offers:

  * Nothing
  * Level 1 Battle
  * Decision
  * Hazard
  * Loot Chest
  * Roll Again

* With Smokescreen active, remove Level 1 Battle and choose from:

  * Nothing
  * Decision
  * Hazard
  * Loot Chest
  * Roll Again

Example: Woods

* Woods normally has Level 1 Battle and Level 2 Battle.
* With Smokescreen active, both battle options are removed.
* Woods should choose from remaining non-battle options.

Reweighting Direction

```js id="drhtkr"
const filteredEvents = availableEvents.filter(
  (event) => !battleEventTypes.includes(event.type)
);

const selectedEvent = weightedRandom(filteredEvents);
```

* Do not leave a “missing” probability gap.
* Do not allow zero-chance events to appear.

Feature Square Requirement

* Smokescreen does not prevent feature battles.
* If the player lands on:

  * Elite Tower
  * Boss Battle
* the feature battle still happens.
* Smokescreen only prevents random environment battle encounters.

Roll Again Requirement

* If Smokescreen is active and the selected event is Roll Again:

  * Smokescreen should continue to protect the same ongoing turn until the eventual landing event resolves.
  * It should not be discarded just because the Roll Again modal appeared.
* Once a non-Roll Again landing event resolves, discard Smokescreen.

Out Of Scope

* No battle prevention beyond the current board turn.
* No change to Elite Tower or Boss Battle.
* No change to battle reward logic.
* No animation required.
* No effect on battles already started.

Testing Checkpoints

* Land on Field repeatedly with event debug.
* Confirm random Level 1 Battle cannot be selected while active.
* Confirm non-battle Field events still work.

* Confirm Level 1 and Level 2 random battles are excluded.
* Land on Forest while active.
* Confirm Level 2 and Level 3 random battles are excluded.
* Land on Elite Tower while active.
* Confirm Elite Tower battle still happens.
* Trigger Roll Again while Smokescreen is active.
* Confirm Smokescreen remains active for the continued turn.

Feature-010: Expand to 4 villages and update village reward rules

Status

* done

Related Feature(s)

* EPIC-016 Feature-004: Implement village visits, village rewards, and village healing
* EPIC-016 Feature-002: Multi-square board features landing/movement/highlighting
* EPIC-020 Feature-011: Add village action choice page
* EPIC-020 Feature-007: Implement SOS potion

Goal

* Update village generation and village reward logic.
* The board should now contain 4 villages:

  * 2 Field Villages in the easy zone.
  * 2 Forest Villages in the hard zone.
* Village rewards should become per-player, once-per-condition rewards.
* Village reward eligibility should be independent for every player.

Village Generation Requirement

* Generate exactly 4 villages:

  * 2 Field Villages.
  * 2 Forest Villages.

* Field Villages should be in the easy zone.

* Forest Villages should be in the hard zone.

* Villages should remain multi-square features if the existing village implementation uses multi-square feature footprints.

Placement Distance Requirement

* Villages must always be at least 12 squares away from any other feature.
* Use orthogonal distance only.
* Do not count diagonal distance.

Features to avoid:

```txt id="e1lna2"
Other villages
Elite Towers
Starting zone
Boss Battle
```

* Distance should use Manhattan distance.
* Suggested formula:

```txt id="a7humh"
distance = abs(x1 - x2) + abs(y1 - y2)
```

Edge Distance Requirement

* Villages must always be at least 3 squares from the edge of the board.
* This means the full village footprint should not be closer than 3 squares from any board edge.
* If village features are 2x2, validate the full footprint, not just the top-left cell.

Placement Failure Requirement

* If the generator cannot place villages with all constraints:

  * retry board generation.
  * or retry village placement.
  * do not silently place invalid villages.
* Avoid infinite loops by using a retry limit and developer warning.

Reward Tracking Requirement

* Village rewards are tracked per player.
* Player 1 collecting a reward has no effect on Player 2.
* Rewards do not reset on death.
* Rewards do not reset on respawn.
* Rewards do not reset when visiting the other village.
* Rewards should persist for the whole game.

Suggested player reward state:

```js id="vll1wz"
villageRewards: {
  fieldVillageLootClaimed: false,
  forestVillageLootClaimed: false,
  firstEliteVillageRewardClaimed: false,
  secondEliteVillageRewardClaimed: false
}
```

Field Village Loot Reward

* First time in the game that a player lands on any Field Village:

  * give that player a Loot Chest.
* After this happens:

  * do not give that player another Field Village first-visit Loot Chest.
  * not from the same Field Village.
  * not from the other Field Village.
  * not after death.
  * not after respawn.

Forest Village Loot Reward

* First time in the game that a player lands on any Forest Village:

  * give that player a Loot Chest.
* After this happens:

  * do not give that player another Forest Village first-visit Loot Chest.
  * not from the same Forest Village.
  * not from the other Forest Village.
  * not after death.
  * not after respawn.

First Elite Tower Village Reward

* When a player defeats their first Elite Tower:

  * the next village they land on should give the first Elite village reward.
* This reward is now:

  * one random common token.
* It is no longer:

  * a potion.
* The existing reward text can remain the same.
* This reward happens once only for that player.
* It does not matter which village they visit.
* After this reward is claimed, it never happens again for that player.

Second Elite Tower Village Reward

* When a player defeats their second Elite Tower:

  * the next village they land on should give the second Elite village reward.
* This reward is:

  * one guaranteed rare token.
* It happens once only for that player.
* It does not matter which village they visit.
* After this reward is claimed, it never happens again for that player.

Elite Count Requirement

* Determine reward eligibility from the player’s own Elite Tower progress.
* Do not use global tower completion.
* A player with one tower defeated should be eligible for the first Elite village reward if not already claimed.
* A player with two towers defeated should be eligible for the second Elite village reward if not already claimed.

Reward Resolution Order

* If multiple village rewards are eligible on the same visit, resolve them in a stable order.

* Preferred order:

  * Field/Forest village-type Loot Chest.
  * first Elite common token reward.
  * second Elite rare token reward.
  * village action choice page from Feature-011.

* This allows a player’s first visit to a village after Elite progress to still receive all eligible queued rewards.

* If this produces too many modal steps, implementation may resolve one reward at a time only if documented, but the preferred behaviour is sequential resolution.

Token Reward Flow

* Common token reward:

  * generate one random common token.
  * use existing token reward display.
  * open token assignment flow if that is the existing token reward behaviour.
  * then continue village sequence.

* Rare token reward:

  * generate one random rare token.
  * use existing token reward display.
  * open token assignment flow if that is the existing token reward behaviour.
  * then continue village sequence.

Loot Chest Flow

* Use existing Loot Chest sequence.
* After Loot Chest completes, return to the village sequence, not directly to board.
* Continue processing remaining rewards or show village action choice page.

Out Of Scope

* Wandsmith implementation; Feature-012 handles it.
* Village action page; Feature-011 handles it.
* No new village artwork required unless existing field/forest village assets need duplication.
* No change to Elite Tower battle logic.
* No change to Loot Chest reward contents.

Testing Checkpoints

* Generate a board.
* Confirm exactly 4 villages exist.
* Confirm exactly 2 Field Villages exist in easy zone.
* Confirm exactly 2 Forest Villages exist in hard zone.
* Confirm all villages are at least 12 orthogonal squares from other features.
* Confirm all villages are at least 3 squares from board edge.
* Player 1 visits first Field Village and gets Loot Chest.
* Player 1 visits second Field Village and does not get another Field Village Loot Chest.
* Player 2 visits a Field Village and still gets their own Field Village Loot Chest.
* Repeat for Forest Villages.
* Player defeats first Elite Tower, then visits a village.
* Confirm random common token reward.
* Confirm this reward happens only once.
* Player defeats second Elite Tower, then visits a village.
* Confirm guaranteed rare token reward.
* Confirm this reward happens only once.
* Confirm death/respawn does not reset village reward collection.
* Confirm village action choice page appears after rewards.
* Confirm there are no console errors.
* Update `testing.txt` before marking this feature done.

* The available actions are:

  * Wandsmith
  * Leave

Page Timing Requirement

* Reward examples:

  * Field Village first-visit Loot Chest.
  * Forest Village first-visit Loot Chest.
  * first Elite village common token reward.
  * second Elite village rare token reward.

Choice Buttons

Rest Behaviour

* The current heal modal and health restore behaviour should be reused.
* After healing completes:

  * return to board.
  * advance to next player.
  * show next-turn modal first.

Wandsmith Placeholder Behaviour

* Clicking Wandsmith should:

  * record that Wandsmith was chosen for same-village lock rules.
  * end the player’s turn.
  * return to board.
  * advance to next player.
  * show next-turn modal first.

* Feature-012 replaces this placeholder with full Wandsmith behaviour.

Leave Behaviour

* Leave acts like a cancel/no-action option.
* Leave is never disabled.
* Clicking Leave should show a modal:

English:

```txt id="n5l0o3"
You left the village
```

Japanese:

```txt id="dkctg6"
村を出ました。
```

* The text should use `larger-text`.
* Then the player’s turn ends:

  * return to board.
  * advance to next player.
  * show next-turn modal first.

Same-Village Option Lock Requirement

* On a player’s first visit to a specific village after a reset:

  * Rest is enabled.
  * Wandsmith is enabled.
  * Leave is enabled.

* If the player visits the same village again without a reset:

  * disable the non-Leave options they already chose at that same village during this lock period.
  * Leave remains enabled.

* Rest can become disabled.

* Wandsmith can become disabled.

* Leave can never become disabled.

Same-Village Lock Example

```txt id="i7gx6q"
1. Player visits Field Village A and chooses Wandsmith.
2. Player later visits Field Village A again without visiting another feature.
3. Wandsmith is disabled, Rest is enabled, Leave is enabled.
4. Player chooses Rest.
5. Player later visits Field Village A again without visiting another feature.
6. Rest and Wandsmith are disabled, Leave is enabled.
7. Player must choose Leave.
8. Future visits to Field Village A still have Rest and Wandsmith disabled until a reset happens.
```

Reset Rules

* The options should re-enable if the player:

  * dies and respawns.
  * visits any other feature.
  * visits a different village.
  * visits an Elite Tower.
  * visits Boss Battle.

* “Any other feature” means the same-village lock should reset when the player’s feature context changes.

* Normal environment squares should not reset the same-village lock.

* Random events on normal environment squares should not reset unless they route to a feature.

Per-Player Requirement

* Track village action lock state per player.
* Player 1’s choices must not affect Player 2.
* Each player has their own same-village history.
