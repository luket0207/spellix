Hazard Chance Rule

* Each environment has its own chance column.
* The chance values determine how likely each hazard is to be produced for that selected environment.
* Example:

  * If `Field` is selected, `Landslide` has `0` chance.
  * If `Field` is selected, `Wildfire` has `18` chance.
* Hazards with `0` chance for the selected environment should not be selected.
* The chance values should be treated as weights.
* They do not need to total 100.
* Select randomly based on the total weight for the selected environment.

Suggested Weighted Selection Logic

```js id="fwvhw7"
function selectHazardForEnvironment(environment, hazards) {
  const weightedHazards = hazards
    .map((hazard) => ({
      ...hazard,
      weight: hazard.chances[environment] ?? 0
    }))
    .filter((hazard) => hazard.weight > 0);

  const totalWeight = weightedHazards.reduce(
    (total, hazard) => total + hazard.weight,
    0
  );

  if (totalWeight <= 0) {
    return null;
  }

  const roll = Math.random() * totalWeight;

  let runningTotal = 0;

  for (const hazard of weightedHazards) {
    runningTotal += hazard.weight;

    if (roll < runningTotal) {
      return hazard;
    }
  }

  return weightedHazards[weightedHazards.length - 1];
}
```

Feature-002: Treat multi-square board features as one logical landing and movement square

Status

* done

Related Feature(s)

* EPIC-002: Procedural board generation
* EPIC-003 Feature-001: Gameplay UI cleanup
* EPIC-004 Feature-005: Board movement and dice movement
* EPIC-016 Feature-001: Add hazard debug trigger and hazard result modal

Goal

* Implement correct landing, highlighting, and movement behaviour for multi-square board features.
* Some board features visually occupy a 2x2 area, but should behave like one logical square.
* Players may visually stand on any cell inside the feature footprint.
* When moving away from the feature, the player should be able to leave from any edge of the footprint without spending extra movement inside the feature.
* When a multi-square feature is in landing range, the whole feature footprint should be highlighted.

Affected Features

* Apply this behaviour to:

```txt id="d9gjnf"
Field Village
Forest Village
Elite Tower Gravel
Elite Tower Woods
Boss Battle
```

* These features should be treated as multi-square logical features.
* For 2x2 features, use all 4 cells in the footprint.
* If Boss Battle currently uses a 3x3 footprint, apply the same logical-square behaviour to all cells in that footprint.
* If Boss Battle has been changed to 2x2, apply the same 4-cell behaviour as the other listed features.

Landing Behaviour

* When a player lands on one of these multi-square features, they should be placed visually on one of the cells inside that feature.
* For 2x2 features, the player can be placed on any of the 4 cells.
* Placement should be random where possible.
* If multiple players are on the same feature, try to place them on different cells within the footprint.
* This reduces player images layering directly on top of each other.

Placement Priority

```txt id="cz4b59"
1. Find all cells inside the feature footprint.
2. Find cells not currently occupied by another player on the same feature.
3. If at least one unoccupied cell exists, randomly choose one of those cells.
4. If all cells are occupied, randomly choose any cell inside the feature footprint.
```

Suggested Landing Logic

```js id="vlxw3t"
function chooseVisualCellForFeature(feature, playersOnFeature) {
  const footprintCells = feature.cells;

  const occupiedCellKeys = new Set(
    playersOnFeature.map((player) => `${player.visualRow}-${player.visualCol}`)
  );

  const availableCells = footprintCells.filter(
    (cell) => !occupiedCellKeys.has(`${cell.row}-${cell.col}`)
  );

  const candidateCells =
    availableCells.length > 0 ? availableCells : footprintCells;

  return randomChoice(candidateCells);
}
```

* Exact implementation can vary.
* The important requirement is that players should spread across the feature cells where possible.

Logical Position Requirement

* These multi-square features should be treated as one logical board square.
* The player’s logical position should represent the feature as a whole.
* The player’s visual position can be one cell inside the feature footprint.
* Movement, highlighting, and encounters should use the logical feature identity, not only the visual cell.

Suggested State Direction

```js id="3djhdl"
player.position = {
  type: "feature",
  featureId: "field-village-001",
  visualCell: {
    row: 12,
    col: 8
  }
};
```

* Exact shape can vary.
* The key distinction is:

  * logical position = the feature.
  * visual position = the cell inside the feature used to display the piece.

Highlighting Requirement

* When a multi-square feature is within movement range, the whole feature footprint should be highlighted.
* This should happen even if only one cell of the feature is technically in range.
* The player should understand they are landing on the whole feature, not on one individual tile.
* The highlight should cover every cell in the feature footprint.

Example

```txt id="sseeus"
A 2x2 Field Village has four cells.

Only the top-left village cell is reachable with the current dice roll.

Result:
All four Field Village cells should be highlighted.
```

Highlighting Behaviour

* If any cell in a multi-square feature footprint is a valid landing destination:

  * mark the logical feature as reachable.
  * highlight every cell in the feature footprint.
* Clicking any highlighted cell in that feature should land the player on the feature as a whole.
* After clicking the feature, choose the player’s visual cell using the landing placement rules.
* Do not require the player to click the exact cell that was originally calculated as reachable.

Suggested Highlight Logic

```js id="mgq3wa"
function expandFeatureHighlights(validDestinationCells, boardFeatures) {
  const highlightedCells = new Set(
    validDestinationCells.map((cell) => `${cell.row}-${cell.col}`)
  );

  for (const feature of boardFeatures) {
    if (!feature.isMultiSquareLogicalFeature) {
      continue;
    }

    const featureIsReachable = feature.cells.some((cell) =>
      highlightedCells.has(`${cell.row}-${cell.col}`)
    );

    if (featureIsReachable) {
      feature.cells.forEach((cell) => {
        highlightedCells.add(`${cell.row}-${cell.col}`);
      });
    }
  }

  return highlightedCells;
}
```

* Exact implementation can vary.
* The important requirement is that partial reachability expands into a full-feature highlight.

Click Handling Requirement

* Clicking any highlighted cell inside a reachable multi-square feature should land the player on that feature.
* The game should not treat different cells of the same feature as different destinations.
* The clicked cell can be ignored for final visual placement if another unoccupied cell is better.
* The final displayed position should still follow the placement priority rules.

Movement Away From Feature Requirement

* When a player starts movement from a multi-square feature, they may leave from any outer edge of the feature footprint.
* Moving out of the feature should cost `1` movement, not extra internal steps.
* The player should not need to move across cells inside the feature footprint.
* The entire feature acts as one square.

Example

* If the player is on a 2x2 village and rolls `1`, valid destinations should include:

  * the two squares directly above the feature.
  * the two squares directly below the feature.
  * the two squares directly left of the feature.
  * the two squares directly right of the feature.

All of those destinations cost:

```txt id="l1ibxa"
1 movement
```

* The player should not be limited by the specific visual cell they are standing on inside the feature.

Valid Exit Squares For 2x2 Feature

For a 2x2 feature:

```txt id="qt6cpb"
[A][B]
[C][D]
```

The roll-1 exit destinations are:

```txt id="qpe50n"
Squares above A and B
Squares below C and D
Squares left of A and C
Squares right of B and D
```

* Each valid adjacent external square costs `1`.
* Internal movement between A, B, C, and D should not count.

Pathfinding Requirement

* When calculating valid movement destinations from a multi-square feature:

  * start the movement frontier from every cell in the feature footprint.
  * treat all footprint cells as movement distance `0`.
  * external adjacent cells cost `1`.
* This makes leaving the feature in any direction cost one movement.

Suggested Pathfinding Direction

```js id="gzir7w"
function getMovementStartCells(playerPosition) {
  if (playerPosition.type === "feature") {
    return getFeatureById(playerPosition.featureId).cells.map((cell) => ({
      ...cell,
      distanceUsed: 0
    }));
  }

  return [
    {
      row: playerPosition.row,
      col: playerPosition.col,
      distanceUsed: 0
    }
  ];
}
```

* Exact implementation can vary.
* The important requirement is that all cells inside the feature footprint act as zero-cost starting cells.

Movement Into Feature Requirement

* When moving into one of these multi-square features, entering any cell in the feature footprint should count as landing on the feature.
