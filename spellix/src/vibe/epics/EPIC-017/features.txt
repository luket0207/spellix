Feature-004: Counter attacks should only trigger when the roller attempts to affect the opponent

Status

* done

Related Feature(s)

* Feature-003: Add rare yellow-outline double-strength tokens
* EPIC-006 Feature-002: Add dice-driven battle turns
* EPIC-011 Bug-010: Battle buffs applied to merged columns must trigger from either merged column number
* EPIC-014 Feature-009: Rearrange battle page with dice between characters

Goal

* Change counter attack behaviour in battle.
* Orange and Orange/Yellow Outline tokens should not always trigger just because the roller matched the opponent’s counter column.
* Counter attack damage should only trigger if the rolling player attempts to affect the opponent that turn.
* Newly applied guard from the same roll should be able to absorb counter damage.

Current Problem

* At the moment, if a player rolls a number and the opponent has counter tokens in that matching column, counter damage is applied regardless of what the player actually did.
* This means a player can take counter damage even if they only guarded or used a self-focused effect.
* That should no longer happen.

Required Counter Trigger Rule

* A counter attack can only trigger if:

  * the rolling player rolls the relevant number.
  * the opponent has Orange or Orange/Yellow Outline counter tokens in the matching effective column.
  * the rolling player attempted to affect the opponent during that same battle turn.

Opponent-Affecting Actions

* The following should count as trying to affect the opponent:

  * dealing damage with Red or Red/Yellow Outline tokens.
  * freezing with Light Blue tokens.
  * applying weakness with Green or Green/Yellow Outline tokens, if weakness targets the opponent.
  * any other current or future token effect that directly targets or harms the opponent.

Non-Opponent-Affecting Actions

* The following should not trigger counter damage by themselves:

  * applying only Guard.
  * charging only.
  * buffing self only.
  * healing self only.
  * missing.
  * any other self-only effect.

Examples

Example 1: Guard only should not trigger counter

```txt id="k9ym13"
Player rolls 2.
Player has 2 Blue tokens in column 2.
Opponent has 1 Orange token in column 2.

Result:
Player gains guard.
No counter damage is applied because the player did not attack or affect the opponent.
```

Example 2: Attack or freeze should trigger counter

```txt id="9auiqv"
Player rolls 4.
Player has Red and/or Light Blue tokens in column 4.
Opponent has Orange token in column 4.

Result:
Player attempted to affect the opponent.
Counter damage is applied.
```

Example 3: Guard from same turn absorbs counter

```txt id="u2pg2r"
Player rolls 1.
Player has 1 Red token and 1 Blue token in column 1.
Opponent has 2 Orange tokens in column 1.

Resolution:
Player deals 10 damage to opponent.
Player gains 5 guard.
Opponent counter deals 10 counter damage.
Player's 5 newly gained guard absorbs 5 counter damage.
Player takes 5 health damage.
Player's guard is reduced to 0.
```

Required Resolution Order

* Within a battle turn, resolve the rolling player’s column effects first.
* Apply the rolling player’s guard before resolving opponent counter damage.
* Then, if the rolling player attempted to affect the opponent, resolve opponent counter damage.
* Counter damage should be absorbed by the rolling player’s current guard, including guard gained earlier in the same turn.

Suggested Resolution Order

```txt id="pzphug"
1. Rolling player rolls dice.
2. Determine rolling player's effective column.
3. Resolve rolling player's effects.
4. Track whether any resolved effect attempted to affect the opponent.
5. Apply any guard gained by the rolling player.
6. If opponent was affected or targeted, check opponent's matching counter column.
7. Apply counter damage.
8. Rolling player's guard absorbs counter damage first.
9. Remaining counter damage reduces rolling player's health.
```

Suggested State Direction

```js id="gnrs7y"
const turnResolution = {
  attemptedToAffectOpponent: false,
  damageToOpponent: 0,
  freezeAppliedToOpponent: false,
  weaknessAppliedToOpponent: 0,
  guardGainedByActor: 0
};
```

Suggested Logic Direction

```js id="h4gwis"
const attemptedToAffectOpponent =
  damageToOpponent > 0 ||
  freezeAppliedToOpponent ||
  weaknessAppliedToOpponent > 0;

if (attemptedToAffectOpponent) {
  applyCounterDamageFromOpponentColumn({
    opponent,
    actor,
    rolledNumber
  });
}
```

Counter Token Values

* Orange token:

```txt id="ykwrtm"
5 counter damage
```

* Orange/Yellow Outline token:

```txt id="sgdwi8"
10 counter damage
```

* Multiple counter tokens stack.

Merged / Joined Column Requirement

* Counter attack checks should use effective column logic.
* If the opponent has a merged or joined column, rolling either number in that effective group should check the correct counter column.
* Do not accidentally check only the visual slot number.

Out Of Scope

* No changes to counter token visual design.
* No changes to counter token animation, except it may trigger less often.
* No changes to Red, Blue, Green, or Light Blue base effects.
* No changes to enemy spell data.
* No changes to battle rewards.
* No changes to non-counter battle order except what is required for guard to absorb same-turn counter damage.

Testing Checkpoints

* Set actor column 2 to only Blue tokens.
* Set opponent column 2 to Orange tokens.
* Roll 2.
* Confirm actor gains guard.
* Confirm no counter damage is applied.
* Set actor column 4 to Red token.
* Set opponent column 4 to Orange token.
* Roll 4.
* Confirm actor damages opponent.
* Confirm counter damage is applied.
* Set actor column 4 to Light Blue token.
* Set opponent column 4 to Orange token.
* Roll 4.
* Confirm freeze attempts to affect opponent.
* Confirm counter damage is applied.
* Set actor column 1 to Red and Blue.
* Set opponent column 1 to 2 Orange tokens.
* Roll 1.
* Confirm actor deals 10 damage.
* Confirm actor gains 5 guard.
* Confirm opponent counter damage totals 10.
* Confirm 5 guard absorbs 5 counter damage.
* Confirm actor takes only 5 health damage.
* Test Orange/Yellow Outline.
* Confirm it deals 10 counter damage.

* Test joined enemy columns.
* Confirm counter checks use effective column numbers.

Implementation Notes

Feature-007: Smooth token glow animation

Status

* done

Related Feature(s)

* Feature-003: Add rare yellow-outline double-strength tokens
* Feature-006: Correct token names and separate them from descriptions
* EPIC-003 Feature-002: Add spell token assignment system

Goal

* Improve the glow animation on tokens.
* The current glow looks jagged and appears to happen in two separate stages.
* The glow should feel smooth, continuous, and polished.

Problem Summary

* Token glow animation currently looks like it jumps between states.
* It may be caused by:

  * too few keyframe steps.
  * abrupt `box-shadow` changes.
  * competing transitions and animations.
  * class changes restarting the animation.
  * glow being applied to both parent and child elements.
  * border changes affecting layout.
* The final visual should be one smooth pulse rather than a two-stage flicker.

Required Behaviour

* Token glow should smoothly pulse in and out.
* The animation should not jump halfway through.
* The token should not visually resize in a jagged way.
* The glow should not affect layout.
* The animation should work for:

  * normal tokens.
  * shiny yellow-outline tokens.
  * reward tokens.
  * token bag tokens.
  * spell assignment tokens.
  * committed spell display tokens.
  * battle spell column tokens.

Implementation Direction

* Refactor the glow into a single reusable class.
* Prefer animating `box-shadow`, `filter: drop-shadow`, `opacity`, or a pseudo-element.
* Avoid rapidly changing layout properties such as:

  * `width`
  * `height`
  * `border-width`
  * `margin`
  * `padding`
* If scaling is used, use a very small smooth scale range and keep it on `transform`.

Suggested CSS Direction

```css id="2k88gq"
.token-glow {
  animation: tokenGlowPulse 1.6s ease-in-out infinite;
  will-change: filter, box-shadow, transform;
}

@keyframes tokenGlowPulse {
  0% {
    filter: drop-shadow(0 0 2px currentColor);
    transform: scale(1);
  }

  50% {
    filter: drop-shadow(0 0 10px currentColor);
    transform: scale(1.04);
  }

  100% {
    filter: drop-shadow(0 0 2px currentColor);
    transform: scale(1);
  }
}
```

Alternative Pseudo-Element Direction

* If `box-shadow` or `filter` still looks jagged, use a pseudo-element behind the token.
* This often gives a smoother glow because the token itself does not need to resize or repaint as heavily.

```css id="zilhfo"
.token-wrapper {
  position: relative;
}

.token-wrapper.is-glowing::before {
  content: "";
  position: absolute;
  inset: -6px;
  border-radius: 50%;
  background: currentColor;
  opacity: 0.25;
  filter: blur(8px);
  animation: tokenGlowAura 1.6s ease-in-out infinite;
  pointer-events: none;
  z-index: -1;
}

@keyframes tokenGlowAura {
  0% {
    opacity: 0.15;
    transform: scale(0.95);
  }

  50% {
    opacity: 0.45;
    transform: scale(1.08);
  }

  100% {
    opacity: 0.15;
    transform: scale(0.95);
  }
}
```

Smoothness Requirement

* The glow animation should use:

  * one continuous animation.
  * `ease-in-out`.
  * matching start and end states.
  * no abrupt change at `50%`.
* The first and last keyframes must match so the loop does not snap.

Important Keyframe Rule

```txt id="5wc2qc"
0% and 100% should be visually identical.
```

* This prevents the glow from jumping when the animation loops.

Avoid Two-Stage Animation

* Check that the token is not receiving two glow animations at the same time.
* Avoid combining:

  * one animation on the token.
  * another animation on the token image.
  * another transition on hover/active state.
* If multiple glow classes exist, consolidate them.

Shiny Token Requirement

* Shiny yellow-outline tokens should keep their `2px` yellow border.
* The glow should not make the yellow border jump or resize.
* Use `box-sizing: border-box` on shiny tokens if needed.

```css id="iiv2u0"
.token-yellow-outline {
  border: 2px solid #F5FA00;
  box-sizing: border-box;
}
```

* The glow should sit outside the token visually and not alter the token’s dimensions.

Performance Requirement

* Avoid expensive layout recalculation during the glow.
* Prefer `transform`, `opacity`, and `filter`.
* Add `will-change` only to the glowing token or aura element, not every token permanently if performance becomes worse.
* Do not trigger React state updates every animation frame.
* The glow should be pure CSS once started.

Expected Behaviour

* Token glow pulses smoothly.
* The glow no longer appears to happen in two stages.
* The token does not jump or flicker.
* The animation loops cleanly.
* Normal tokens still look the same apart from the smoother glow.
* Shiny tokens keep their yellow outline and glow smoothly.
* Token tooltips and click/drag behaviour are unaffected.

Out Of Scope

* No changes to token effects.
* No changes to token rarity.
* No changes to token names or descriptions.
* No changes to token assignment rules.
* No changes to battle animations.
* No changes to reward odds.
* No unrelated token redesign.
