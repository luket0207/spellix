Feature-001: Add persistent random background music

Status

* not started

Related Feature(s)

* EPIC-018 Feature-012: Only show settings button on gameplay page
* EPIC-019 Feature-014: Add rules modal inside settings menu
* App shell / routing / settings menu

Goal

* Add background music to the game.
* The user has added 10 songs into:

```txt id="ayzr7c"
src/music/
```

* Music should automatically start if possible.
* Music should continue playing regardless of which page the player is on.
* Add a Music section to the settings menu.
* The Music section should include a pause/play button.
* Songs should play in random order.
* Every song should play once before any song is repeated.

Browser Autoplay Note

* Modern browsers often block audio autoplay until the player interacts with the page.
* The game should still try to start music automatically.
* If autoplay is blocked:

  * do not crash.
  * do not show console errors as app errors.
  * wait for the first user interaction.
  * then start music automatically unless the player has manually paused it.

Required Behaviour

* Music should start automatically when the game opens if the browser allows it.
* If autoplay is blocked, music should start after the first player interaction.
* Music should continue across page changes.
* Music should not restart from the beginning every time the route changes.
* Music should not create multiple overlapping audio instances.
* The player should be able to pause and resume music from settings.
* If the player pauses music manually, it should stay paused until they press play again.
* If the current song ends, the next song should start automatically.

Persistent Music Requirement

* The music player should live at the app shell/context level.

* It should not be mounted inside individual pages such as:

  * gameplay.
  * battle.
  * rules.
  * village.
  * cave.
  * river.
  * decision.
  * loot chest.
  * winner page.

* Route changes should not unmount the music system.


* The important rule is that music state and the audio element survive route changes.

Music Files Requirement

* Load all 10 songs from `src/music/`.
* Store them in a single music track list.
* The track list should be the source of truth for available songs.
* If the project uses Vite, `import.meta.glob` can be used.
* If explicit imports are easier, use explicit imports.

Suggested explicit import direction:

```js id="k7kdj0"

import song2 from "../music/song2.mp3";

  song1,

```

Suggested Vite glob direction:

```js id="xk0hwq"

  eager: true,
  query: "?url",
  import: "default"
});

export const musicTracks = Object.values(musicModules);
```

* Use the approach that fits the project setup.
* Do not hard-code only one song.
* Do not rely on the browser randomly selecting files from a folder without importing them.

Random Order Requirement

* Songs should play in a random order.
* Every song should play once before any song repeats.
* Use a shuffled bag/queue.
* When the queue is empty, create a new shuffled queue from all songs.

Correct Shuffle Behaviour

```txt id="hk7sy5"
1. Start with all 10 songs.
2. Shuffle them.
3. Play each song once.
4. When all 10 have played, create a new shuffled list.
5. Start the next cycle.
```

* A song should not appear twice within the same 10-song cycle.
* The next cycle does not need to use the same order as the previous cycle.
* If possible, avoid making the first song of the new cycle the same as the final song of the previous cycle.
* If avoiding that is awkward, it is acceptable as long as each full cycle still contains all songs once.

Example Valid Cycle

```txt id="ygwx0g"
Song 2
Song 4
Song 7
Song 10
Song 1
Song 3
Song 9
Song 8
Song 6
Song 5
```

Example Next Valid Cycle

```txt id="ztyijv"
Song 4
Song 10
Song 3
Song 2
Song 7
Song 8
Song 5
Song 1
Song 6
Song 9
```

Important

* The illustrative example in the request should be interpreted as “random order”.
* The implementation rule is stricter:

  * all 10 songs should play once before repeats.
  * no duplicates inside one cycle.

Suggested Shuffle Helper

```js id="m4cotv"
function shuffleTracks(tracks) {
  const shuffled = [...tracks];

  for (let index = shuffled.length - 1; index > 0; index -= 1) {
    const randomIndex = Math.floor(Math.random() * (index + 1));
    [shuffled[index], shuffled[randomIndex]] = [
      shuffled[randomIndex],
      shuffled[index]
    ];
  }

  return shuffled;
}
```

Playback Flow

```txt id="c2x4hz"
1. App loads.
2. MusicProvider creates a shuffled queue from all songs.
3. MusicProvider selects the first track.
4. MusicProvider attempts to play.
5. If play succeeds, music continues.
6. If play is blocked, wait for first user interaction.
7. When a song ends, select the next song in the queue.
8. When the queue is empty, create a new shuffled queue.
9. Continue until player pauses music.
```

Autoplay Block Handling

* Attempt to call `audio.play()`.
* If the promise rejects:

  * set `autoplayBlocked` to true.
  * wait for a click/touch/keydown interaction.
* On first interaction:

  * try to play again.
  * only do this if `userPaused` is false.
* Remove first-interaction listeners after successful playback or once no longer needed.

Suggested Direction

```js id="k15tig"
audio.play().catch(() => {
  setAutoplayBlocked(true);
});
```

* Do not repeatedly spam play attempts every render.
* Do not create an infinite loop of failed autoplay attempts.

* No volume control is required in this feature.
* Use a sensible default volume.
* If the project already has a default audio volume constant, use it.

Error Handling

* If one music file fails to load:

  * skip that track.
  * continue with the next track if possible.
  * log a developer warning.
* If no tracks can be loaded:

  * music controls can be hidden or disabled.
  * do not crash the app.

Feature-004: Fix overflowing modal action button positioning

Status

* not started

Related Feature(s)

* EPIC-020 Feature-001: Make gameplay layout scale to fit screen height
* EPIC-020 Feature-014: Add rules modal inside settings menu
* EPIC-020 Feature-015: Prevent horizontal scrollbar in spells modal during token drag
* Settings modal
* Debug menu modal

Goal

* Fix modal layouts when the modal content overflows on the y axis.
* Action buttons should never be placed over the top of overflowing modal content.
* Action buttons should always appear at the bottom of the modal content.
* A clear example of the current problem is the Close button at the bottom of the debug menu.

Problem Summary

* Some modals now overflow vertically.
* When this happens, the modal action buttons can overlap the overflowing content.
* This makes the content harder to read and can make the buttons feel incorrectly positioned.
* The modal should treat action buttons as part of the content flow, not as an overlay on top of the content.

Required Behaviour

* Modal action buttons should always appear after the modal content.
* Buttons should not cover text, form controls, debug options, token lists, potion lists, or any other modal content.
* If a modal needs vertical scrolling:

  * the content should scroll safely.
  * the buttons should remain reachable.
  * the buttons should still appear at the bottom of the content.
* The Close button in the debug menu should appear below all debug content, not over it.

Important Layout Rule

* Action buttons should not be absolutely positioned over modal body content.
* Action buttons should not use fixed positioning inside the modal.
* Action buttons should not float above scrollable content.
* Action buttons should participate in the normal modal layout flow.

Correct Layout Direction

```txt id="v85xi2"
Modal container
Modal title
Modal body content
Modal action buttons
```

Incorrect Layout Direction

```txt id="z38ue9"
Modal container
Modal title
Modal body content
Action buttons visually overlaying the body content
```

Suggested Structure

```jsx id="ol84vu"
<div className="modal-background">
  <div className="modal-content">
    <div className="modal-body">
      {content}
    </div>

    <div className="modal-actions">
      {buttons}
    </div>
  </div>
</div>
```

Suggested CSS Direction

```css id="e7cddp"
.modal-content {
  display: flex;
  flex-direction: column;
  max-height: calc(100vh - 48px);
  overflow-y: auto;
}

.modal-body {
  position: relative;
}

.modal-actions {
  position: relative;
  display: flex;
  justify-content: center;
  gap: 20px;
  margin-top: 40px;
  padding-bottom: 20px;
  flex-shrink: 0;
}
```

Debug Menu Requirement

* The debug menu should be specifically checked.
* The Close button at the bottom of the debug menu should:

  * appear after all debug menu content.
  * not overlay the debug controls.
  * be reachable by scrolling if the debug menu is taller than the screen.
  * keep the existing button style.

Scrollable Modal Requirement

* For long modals, prefer this behaviour:

  * the modal panel has a maximum height.
  * the panel scrolls vertically.
  * the buttons are at the end of the scrollable content.
* Do not pin the buttons on top of the content unless a future feature explicitly asks for a sticky footer.

Button Group Requirement

* Existing modal button styling should be preserved.
* Buttons should remain bottom-centred unless a specific modal has a different existing layout requirement.
* Multiple action buttons should keep their existing horizontal or vertical arrangement.
* Secondary/cancel buttons should keep their secondary style.

Affected Areas To Check

* Rules modal inside settings.
* Potion confirmation modals.
* Potion replacement modals.
* Token assignment modals.
* Wandsmith/spells modal.
* Loot Chest reward modals.
* Decision outcome modals.

Out Of Scope

* No redesign of modal visuals.
* No change to modal background images.
* No change to button text.
* No change to modal behaviour.
* No change to horizontal overflow handling, except where already covered by EPIC-020 Feature-015.

Feature-005: Hide normal potions section when Active Potion section is visible

Status

* not started

Related Feature(s)

* EPIC-012 Feature-002: One potion per turn limits and Active Potion section
* EPIC-013 Feature-004: Starting Charge potion behaviour
* EPIC-013 Feature-008: Double Dice and Triple Dice
* EPIC-020 Feature-008: Implement Metal Detector potion
* EPIC-020 Feature-009: Implement Smokescreen potion

Goal

* Simplify the gameplay potion UI.
* When the Active Potion section is visible, the normal potions section should be hidden.
* This prevents the UI from becoming too tall and helps with the responsive layout changes.

Required Behaviour

* If the current player has an active potion shown in the Active Potion section:

  * hide the normal potions section.
  * show only the Active Potion section.
* If the current player does not have an active potion:

  * show the normal potions section as usual.
  * hide the Active Potion section.

Definition Of Normal Potions Section

* The normal potions section is the gameplay UI area that shows the player’s available potion slots.
* This includes:

  * potion slot display.
  * available board potion Use buttons.
  * empty potion slots.
  * potion tooltips.

Definition Of Active Potion Section

* The Active Potion section is the gameplay UI area introduced for potions that are currently affecting this turn.
* Examples include:

  * Starting Charge.
  * Roll Choice after selecting a roll.
  * Double Dice.
  * Triple Dice.
  * Spellbound effect on target.
  * Heavy Weight effect on target.
  * Troublemaker while waiting for roll.
  * Devine Chance while waiting for roll.
  * Storm Master while waiting for roll.
  * Metal Detector.
  * Smokescreen.

Display Rule

```txt id="0u9wfc"
Active Potion visible = hide normal potions section
Active Potion hidden = show normal potions section
```

Suggested JSX Direction

```jsx id="vwcm4d"
const hasActivePotion = Boolean(currentPlayer.activePotion);

return (
  <div className="gameplay-potion-area">
    {!hasActivePotion && (
      <NormalPotionsSection player={currentPlayer} />
    )}

    {hasActivePotion && (
      <ActivePotionSection activePotion={currentPlayer.activePotion} />
    )}
  </div>
);
```

* Use the actual project state names.
* If the active potion state supports multiple active potions, hide the normal section whenever the active potion list is not empty.

Potion Use Rules

* This feature only changes visibility.
* It does not change potion-use logic.
* If a potion is active, the player should not see or use normal board potion buttons until the Active Potion section clears.
* Existing one-board-potion-per-turn logic still applies.
* Existing one-battle-potion-per-turn logic still applies separately.

Turn Flow Requirement

* When the active potion resolves and is removed:

  * the normal potions section may become visible again if the same player is still in a valid pre-roll gameplay state.
* If the turn advances:

  * the next player’s potion UI should render according to their own active potion state.

Responsive Layout Requirement

* Hiding the normal potions section should reduce vertical space used by the gameplay UI.
* Do not leave a large empty gap where the normal potions section was hidden.
* The Active Potion section should occupy the potion area cleanly.

Out Of Scope

* No changes to potion data.
* No changes to potion effects.
* No changes to potion limits.
* No changes to battle potion section.
* No redesign of Active Potion component.

Feature-006: Show token bag capacity and use Unkempt for Japanese spell column numbers

Status

* not started

Related Feature(s)

* EPIC-003 Feature-002: Add spell token assignment system
* EPIC-010 Feature-015: Redesign Spell Token Assignment page
* EPIC-011 Feature-008: Spell Token Assignment must display merged columns as one effective droppable column
* EPIC-020 Feature-012: Implement Wandsmith village option
* EPIC-020 Feature-017: Change Japanese font to M PLUS Rounded 1c

Goal

* Improve clarity in the spells modal and modifying spells component.
* Show the token bag capacity next to the Token Bag title.
* Ensure spell column capacity numbers use `Unkempt` font in Japanese.
* Numbers should always use `Unkempt`.

Part 1: Token Bag Capacity Display

Required Behaviour

* In the spells modal and modifying spells component, display the token bag capacity next to the token bag title.
* If the token bag is empty and has 5 total spaces, show:

English:

```txt id="sb10ue"
Token Bag 0/5
```

Japanese:

```txt id="0f5zi0"
トークンバッグ 0/5
```

* The first number is the number of tokens currently in the token bag.
* The second number is the token bag’s maximum capacity.

Capacity Format

```txt id="a2ohh6"
{title} {currentCount}/{maxCapacity}
```

Examples:

```txt id="3viyrn"
Token Bag 0/5
Token Bag 3/5
Token Bag 5/5
```

Japanese examples:

```txt id="7r1yl5"
トークンバッグ 0/5
トークンバッグ 3/5
トークンバッグ 5/5
```

Where This Should Appear

* Normal spells modal.
* First spell assignment.
* Wandsmith spells modal.
* Redo potion spell modification modal.
* Any modifying spells component that shows the token bag.
* Any reward token assignment version if it uses the same token bag component.

Suggested JSX Direction

```jsx id="oswozu"
<h2 className={`token-bag-title ${languageClass}`}>
  {language === "jp" ? "トークンバッグ" : "Token Bag"}{" "}
  <span className="number-text">
    {tokenBag.length}/{tokenBagCapacity}
  </span>
</h2>
```

* Use the real token bag array/state names.
* Use the real capacity source of truth.
* Do not hard-code `5` if token bag capacity can change in the future.

Token Bag Capacity Source Of Truth

* Use the current token bag maximum capacity from player state or game constants.
* If token bag max capacity is always 5 right now, it is acceptable to use the existing constant.
* If future features allow token bag capacity changes, this display should update automatically.

Part 2: Numbers Should Always Use Unkempt

Required Behaviour

* Numbers in the spells modal should use `Unkempt`, even in Japanese.
* Specifically, the capacity numbers for spell columns in the Japanese version should use `Unkempt`.
* The token bag capacity numbers should also use `Unkempt`.
* This rule applies to numeric text, not necessarily surrounding Japanese labels.

Examples

Japanese token bag title:

```txt id="xkd0fo"
トークンバッグ 3/5
```

* `トークンバッグ` should use the Japanese font.
* `3/5` should use `Unkempt`.

Japanese spell column capacity:

```txt id="2i7fug"
2/5
```

* `2/5` should use `Unkempt`.

CSS Requirement

* Add or reuse a class for number text.

Suggested CSS:

```css id="9yr28d"
.number-text,
.capacity-number,
.token-bag-capacity,
.spell-column-capacity {
  font-family: "Unkempt", cursive;
}
```

* Use more specific selectors if the Japanese font class overrides this.
* Numbers should remain readable and aligned.

Suggested More Specific CSS

```css id="nyu8ea"
.jp .number-text,
.jp .capacity-number,
.jp .token-bag-capacity,
.jp .spell-column-capacity {
  font-family: "Unkempt", cursive;
}
```

Spell Column Capacity Requirement

* In Japanese, any spell column capacity number should use `Unkempt`.
* This includes:

  * normal columns.
  * edge columns.
  * columns affected by Grey capacity.
  * merged/effective columns.
  * Wandsmith mode.
  * Redo mode.
  * first spell assignment.
  * reward token assignment if spell columns are shown.

Merged Column Requirement

* Merged column labels such as `1+2` should also use `Unkempt` because they are numeric.
* Capacity values on merged columns should use `Unkempt`.
* Do not let merged column labels switch to Japanese font.

Examples:

```txt id="mq28km"
1+2
2+3
5/6
```

* All of these should use `Unkempt`.

Language Requirement

* English:

  * token bag title can continue using existing English font.
  * numbers should use `Unkempt`, which should already match the English numeric style.

* Japanese:

  * Japanese words should use Japanese font from EPIC-020 Feature-017.
  * numbers should use `Unkempt`.

Out Of Scope

* No change to token bag capacity rules.
* No change to spell column capacity rules.
* No change to Grey capacity behaviour.
* No change to White merge behaviour.
* No change to spell modal layout beyond capacity text.
* No change to token drag-and-drop.
* No change to Wandsmith functionality.
