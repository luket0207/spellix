BOARD GAME REACT AGENT RULES

Purpose
- Build a functional React board game style webapp without making design decisions unless the user explicitly asks for design work.
- Keep the app as lo-fi as possible by default.
- Prioritise gameplay logic, state flow, user actions, routing, and testable behaviour.
- Avoid visual polish, styling systems, branding, animation, decorative UI, or theme decisions unless specifically requested.
- Keep every coding pass small, controlled, and directly tied to the exact instruction given.
- Prevent the coding agent from adding extra features, extra abstractions, speculative improvements, or unrequested design work.
- Keep features easy to review, debug, extend, and redesign later.

Project Default
- This is a React project for a board game style game.
- The default implementation style is functional, plain, and low fidelity.
- The app should work before it looks good.
- Visual quality is not part of the task unless the prompt explicitly says so.
- Do not infer a finished board game theme from the concept of the game.
- Do not choose a visual identity, palette, typography style, layout style, animation style, illustration style, icon style, card style, or board style unless the user explicitly provides it.
- When UI is required, use the simplest functional layout that makes the feature usable.
- Default browser styling is acceptable unless the user asks for more.
- Temporary lo-fi UI is acceptable if it clearly supports the required behaviour.

Core Principles
- Functionality first.
- Reuse first: always check existing components, layouts, hooks, utilities, data files, and styles before creating new ones.
- Small focused files: avoid large multi-purpose files.
- Single responsibility: each file should do one clear job.
- Consistent style: follow existing project patterns and naming.
- No hidden magic: keep logic explicit and traceable.
- Prefer simple, readable code over clever abstractions.
- Build features in small shippable increments.
- Do not introduce new dependencies unless there is a clear reason and the existing stack cannot solve the problem cleanly.
- Do exactly what was requested, no more and no less.
- Treat the user's prompt as the scope boundary for the current coding pass.
- Do not expand the task based on assumptions about future features.
- Do not improve unrelated areas of the app while completing a requested feature.
- Do not add "nice to have" functionality unless it was explicitly requested.
- If something seems useful but was not requested, note it as a follow-up instead of implementing it.

No Design Decision Rules
- Do not make design decisions unless explicitly instructed.
- Do not choose colours.
- Do not choose fonts.
- Do not choose spacing scales.
- Do not choose visual themes.
- Do not choose board game art direction.
- Do not choose card visual styles.
- Do not choose token visual styles.
- Do not choose icon sets.
- Do not choose animation styles.
- Do not choose decorative layouts.
- Do not choose gradients, shadows, borders, rounded corners, textures, backgrounds, or other polish.
- Do not create a design system.
- Do not create design tokens unless explicitly requested.
- Do not create a theme file unless explicitly requested.
- Do not add visual variants unless explicitly requested.
- Do not improve visual appearance as a side effect of functional work.
- Do not redesign existing UI unless the prompt explicitly asks for a redesign.
- Do not infer that "board game style" means decorative board game styling.
- Treat "board game style" as a functional product category unless the user provides visual direction.
- If the user asks for a board, card, player area, score area, or game screen, implement the minimum functional structure needed to interact with it.
- If visual decisions are unavoidable, choose the plainest possible option and document the assumption.

Lo-Fi UI Rules
- UI should be plain, readable, and functional.
- Prefer simple HTML elements where they are enough.
- Use existing components if they already exist.
- Keep layout simple: vertical stacks, basic sections, plain buttons, plain tables, plain lists, plain forms.
- Avoid decorative UI.
- Avoid unnecessary responsive complexity.
- Avoid animations unless required for gameplay or explicitly requested.
- Avoid custom styling unless required for usability.
- Avoid adding images, icons, or artwork unless explicitly requested.
- Avoid placeholder artwork.
- Avoid fake board game visuals.
- Avoid polished card layouts unless specifically requested.
- Use text labels instead of icons by default.
- Use visible basic controls instead of hidden gestures or clever interactions.
- Keep user-facing text clear and practical.
- Do not spend effort making the UI attractive unless the prompt asks for design.

Hard Scope Control Rules
- The coding agent must only implement the specific feature, fix, or change requested in the current prompt.
- Do not add additional features, screens, flows, data models, styling systems, helper layers, or abstractions unless explicitly requested.
- Do not perform opportunistic refactors outside the files required for the current task.
- Do not redesign existing UI unless the prompt explicitly asks for a redesign.
- Do not change app structure unless the prompt explicitly asks for structure changes or the task cannot work without the smallest possible structure change.
- Do not introduce new architecture in anticipation of future requirements.
- Do not add placeholder features for later unless specifically requested.
- Do not add demo content, example screens, fake navigation, or sample flows unless the prompt asks for them.
- Do not add extra validation, extra states, extra settings, or extra controls beyond what was requested.
- Do not create generic systems when a small feature-level implementation is enough.
- Do not create "just in case" utilities, hooks, context providers, constants files, config files, or data models.
- Do not modify unrelated files to make the app "cleaner" during a feature pass.
- Do not rename files, components, props, routes, or folders unless the prompt asks for it or it is strictly required to complete the task.
- Do not change existing behaviour unless the current task explicitly requires that behaviour to change.
- If the requested change reveals a possible improvement outside scope, record it as a follow-up instead of implementing it.
- If the prompt is ambiguous, choose the smallest reasonable interpretation and document the assumption.
- When in doubt, implement less and report what remains.

Incremental Delivery Rules
- Each prompt should result in one small, reviewable change.
- Prefer the smallest working implementation that satisfies the prompt.
- Finish the requested increment before touching anything else.
- Stop once the requested behaviour works.
- Do not continue into the next logical feature unless the prompt explicitly asks for it.
- Do not combine multiple unrelated improvements into one pass.
- Keep changes easy to inspect in a diff.
- Avoid large rewrites unless the prompt explicitly asks for a rewrite.
- If a task seems large, split the work into the smallest useful slice and complete only the slice requested.
- If a future step is obvious, mention it in notes rather than implementing it.
- If a feature requires setup and implementation, do the minimum setup needed for the current feature only.
- A coding pass is successful when the requested change works, not when the surrounding area has been fully improved.
- A coding pass is not successful if it adds unrequested design, polish, or extra scope.

Stop Rules For The Coding Agent
- Stop coding when the requested change is complete.
- Stop coding before starting any adjacent feature.
- Stop coding before performing broad cleanup outside the touched area.
- Stop coding before adding optional enhancements.
- Stop coding before introducing a new dependency.
- Stop coding before creating a new shared abstraction unless explicitly required.
- Stop coding before making styling or design improvements unless explicitly requested.
- Stop coding if the next step would require guessing user intent.
- Stop coding if the next step belongs in a different feature or epic.
- Report back with:
  - What was changed
  - Files changed
  - What was intentionally not changed
  - Any assumptions made
  - Any follow-up work that should be handled separately
  - Any checks run
  - Any checks not run and why

- Do not create `.ts` files.
- Do not create React component files with the `.js` extension.

- Use the project's existing package manager, scripts, router setup, styling setup, and folder conventions.

- Do not introduce another UI library unless explicitly approved.
- Do not introduce a state management library unless explicitly approved.
- Do not introduce an animation library unless explicitly approved.
- Do not introduce a styling framework unless explicitly approved.

Component Reuse Rules
- Before building a new component, check whether an existing component can be reused or extended.
- Prefer reusable existing components for common UI patterns such as:
  - Page layouts
  - Buttons
  - Forms
  - Dialogs/modals
  - Tables/lists
  - Empty states
  - Loading states
  - Error messages
  - Navigation elements
- If a component is likely to be used in more than one feature, place it in a shared/common component area only when reuse is immediate or explicitly requested.
- If a component is specific to one feature, keep it inside that feature folder.
- Do not duplicate components with only minor wording or styling differences.
- When creating a reusable component, keep it flexible but not over-engineered.
- Prefer composition over large configurable components with too many props.
- Do not promote a feature component to shared just because it might be reused later.
- Do not build a component library during a feature pass unless explicitly requested.
- Do not create styled wrapper components just to make the UI look better.

Shared Component Promotion Rules
- Start components inside the feature that needs them.
- Promote a component to `src/components/` only when it is reused now or clearly required by the current task.
- Do not over-generalise a component before it has a second real use case.
- Do not promote components based only on possible future reuse.
- When promoting a component, update imports and remove duplicate feature-level versions.
- Document the promotion in the relevant `features.txt` or `testing.txt` only if it materially affects the current feature.
- If promotion is not required for the current prompt, keep the component feature-local.

Code Quality Rules

  - Utilities/helpers: target <= 150 lines
  - Hooks: target <= 150 lines
  - Game logic files: target <= 200 lines
- If bigger, split into smaller files.
- Keep gameplay and business logic out of JSX markup where practical.
- Extract repeated logic to shared helpers/hooks only when repetition exists now.
- Do not create helper functions for hypothetical future reuse.
- Do not duplicate utility logic that already exists.
- Use clear names. Avoid vague names like `data2`, `temp`, `stuff`, `thing`, or `misc`.
- Remove dead code and stale comments in files directly touched by the task.
- Do not clean unrelated files.
- Leave concise comments only where logic is genuinely non-obvious.
- Keep imports tidy and remove unused imports in touched files.
- Avoid deeply nested JSX where smaller components would be clearer.
- Avoid deeply nested conditionals where helper functions would be clearer.
- Do not add comments explaining obvious code.
- Do not add speculative TODOs unless they relate directly to a known follow-up from the current prompt.

- Keep the three-file workflow simple:
  - `features.txt` tracks planned and completed feature scope.
  - `bugs.txt` tracks bugs, investigation, and fixes.
  - `testing.txt` tracks manual and automated testing.

Epic Tracking Structure
- Each epic should use this structure:
  - `src/vibe/epics/<epic-name>/features.txt`
  - `src/vibe/epics/<epic-name>/bugs.txt`
  - `src/vibe/epics/<epic-name>/testing.txt`
- Do not add an `implementation.txt` file.
- Do not add extra process files unless the user explicitly requests them.
- Do not create project memory/index files unless the user explicitly requests them.
- If the project already has an older overview or implementation file, ignore it unless the user asks to migrate or delete it.

features.txt
- List every feature/sub-feature needed to complete the epic.
- Keep items small enough to implement in one focused pass.
- Include status markers:
  - `not started`
  - `in progress`
  - `done`
  - `blocked`
- Include notes on when to stop implementation and start testing.
- Include basic testing checkpoints where useful.
- Include brief completion notes when a feature is done.
- Include assumptions when they affect the feature.
- Include follow-up notes only when they are clearly outside the current scope.
- Do not mark a feature done until testing notes are updated.
- Do not add new features to `features.txt` unless the user has requested them or they are required to break down the current epic.
- Do not use `features.txt` as a place to invent extra scope.
- Do not use `features.txt` as a design document unless the user explicitly asks for design planning.
- Do not document unrequested visual design decisions.

bugs.txt
- Track bugs related to the epic only.
- Each bug entry should include:
  - Bug title
  - Repro steps
  - Expected behaviour
  - Actual behaviour
  - Suspected cause
  - Attempted fixes
  - Final fix if solved
  - Status:
    - `not started`
    - `investigating`
    - `attempted`
    - `fixed`
    - `blocked`
- Do not fix unrelated bugs unless the current prompt asks for it.
- If an unrelated bug is discovered, record it as a follow-up or bug entry only if relevant.
- Do not redesign UI while fixing bugs unless the bug is specifically a UI/design bug.
- Bug fixes should use the smallest safe change.

testing.txt
- Must be updated after every feature implementation.
- For each feature, include:
  - Manual test steps written for a non-developer to follow
  - Expected result for each step
  - Automated tests completed where relevant
  - Automated tests still needed to fully prove behaviour
  - Test status:
    - `not started`
    - `in progress`
    - `passed`
    - `failed`
    - `blocked`
- Testing notes should cover the requested feature only.
- Do not add broad regression plans unless the prompt asks for regression testing or the epic is being completed.
- Testing should confirm behaviour, not visual polish, unless visual polish was explicitly requested.
- If the UI is intentionally lo-fi, do not mark that as a test failure.

Epic Completion Gate
- An epic is only done when its testing has been run and documented.
- At the end of every epic, execute and record in `testing.txt`:
  - Full manual regression flow for that epic
  - Relevant automated tests proving the epic works as intended
  - Any remaining gaps, with clear next actions
- Do not mark an epic done just because the current feature is done.
- Do not complete adjacent epic work unless the prompt explicitly asks for epic completion.
- Do not create a separate implementation summary file when completing an epic.

Working Agreement While Vibe Coding
- Build in small increments and log progress in epic files continuously.
- Do not jump to new features until current feature notes and testing notes are updated.
- If blocked, log the blocker and next best option instead of guessing silently.
- Prefer shippable progress over large risky rewrites.
- When changing shared systems, note potential impact on other epics.
- Reuse existing components before creating new ones.
- Keep all React component files as `.jsx`.
- Keep the app structure simple until the project genuinely needs more abstraction.
- Keep UI lo-fi unless the user asks otherwise.
- Do not over-engineer early board game features before the real requirements are known.
- Do not let the agent continue working after the requested scope is complete.
- Do not let the agent turn a small prompt into a larger product design exercise.
- Do not let the agent add features just because they seem obvious or helpful.
- Do not let the agent make art direction or design decisions.
- When the current prompt is complete, stop, summarize, and wait for the next instruction.

Standard Prompt Footer For Coding Agent

Add this footer to implementation prompts when using the coding agent:

Scope control:
- Only implement what is explicitly requested in this prompt.
- Do not add extra features, extra screens, extra fields, extra routes, or extra abstractions.
- Do not do unrelated refactors or cleanup.
- Do not future-proof the code beyond the current requirement.
- Do not make design decisions.
- Keep the UI lo-fi and functional unless styling is explicitly requested.
- Do not add colours, fonts, animations, icons, decorative layouts, themes, or visual polish unless explicitly requested.
- Use existing components, hooks, utilities, styles, and patterns before creating new ones.
- All React files must use `.jsx`.
- Pure non-JSX utilities, constants, and mock data may use `.js`.
- Update only the relevant vibe files:
  - `features.txt`
  - `testing.txt`
  - `bugs.txt` if relevant
- Do not create or update `implementation.txt`.
- Stop when the requested change works.
- Report back with files changed, behaviour added, assumptions made, checks run, and anything intentionally left for a future prompt.
